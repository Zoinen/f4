# ttytest — стенд для отладки отрисовки в настоящем терминале

Гоняет f4 в реальном pty и смотрит на него с двух сторон одновременно:
экран через эмулятор терминала (`pyte`) и сырой поток байт, который f4
шлёт наружу. Появился при разборе issue #518 (см. `docs/CURSOR.md`), где
ровно этой пары не хватало: буфер экрана был правильный, а курсора на
экране не было.

Полезен для любых багов, где «выглядит не так»: курсор, атрибуты ячеек,
перерисовка, поведение в простое. Для логики без отрисовки проще и быстрее
обычные Go-тесты.

```
pip install pyte
cd tools/ttytest
./scenarios.py                 # прогнать проверки
./scenarios.py boundary-focus  # прогнать конкретную пробу
```

Бинарь ищется в таком порядке: `$F4_BIN`, затем `f4` в `PATH`, иначе
собирается из репозитория в `tools/ttytest/f4`. Процесс запускается в
`sandbox/work`, а `HOME` ему подставляется `sandbox/home` — настоящий
конфиг не трогается. Каталоги намеренно разные: f4 держит конфиг в `HOME`,
и если совместить, панель показывает `.config` рядом с файлами сценария и
всякое хождение по списку промахивается.

## Проверки и пробы

`scenarios.py` содержит два вида сценариев.

**Проверки** возвращают ok/FAIL, это регрессии по #518 и #863:

| имя | что стережёт |
|---|---|
| `caret-not-under-dialog` | каретка редактора не просвечивает сквозь модальный диалог |
| `caret-follows-focus` | там, где в фокусе поле ввода, каретка видна |
| `caret-survives-long-input` | заполнение поля за его ширину не теряет каретку |
| `cat-keeps-last-line` | `cat` файла без перевода строки в конце показывает и последнюю строку, а родной промпт bash не вылезает из-под командной строки f4 (#863); гоняется в настоящем bash, а не на mock-shell |

**Пробы** ничего не утверждают, а печатают, что произошло, — для случаев,
где правильный ответ ещё не выбран: `boundary-focus` (уход фокуса по
стрелкам на краю текста), `idle` (что f4 шлёт в простое — должен не слать
ничего), `new-file`.

## Разбор чужого лога

Когда воспроизвести на своей машине не выходит, у пользователя просится
сырой лог:

```
script -f /tmp/f4.raw -c f4
```

и разбирается так:

```
./analyze_log.py /tmp/f4.raw [--frames]
```

Скрипт режет поток на кадры по меткам synchronized update и говорит, что
происходило с кареткой. Что он различает:

- **кадр без закрывающей метки** — наш баг: запись оборвалась на полпути, а
  каждый кадр гасит каретку на время отрисовки и возвращает её в конце;
- **каретка скрыта, но все кадры целые** — скорее всего не баг: так и
  должно быть, когда в фокусе кнопка, чекбокс или комбобокс;
- **тишина в потоке в момент пропажи** — не наш баг вовсе: мы не послали
  ничего, значит это терминал, и следующий вопрос — его настройки мигания.

Учтите, что в лог попадает всё содержимое экрана.

## Как писать свой сценарий

```python
from ttytest import Session, F7, RIGHT

with Session() as s:
    s.send(F7)                    # нажать клавишу и дочитать кадры
    s.status("диалог открыт")     # строка: состояние каретки и позиция
    s.dump("экран", rows=(9, 20)) # экран текстом
    s.idle(5)                     # помолчать и посмотреть, что придёт само
    s.wait_for(lambda s: s.has_text("Search"))   # дождаться состояния
    s.caret()                     # (строка, колонка, видима ли)
    s.caret_on_wire()             # что мы сказали терминалу: shown/hidden/unchanged
    s.caret_sequences()           # escape-последовательности этого кадра
    s.types_into_field()          # поле ещё в фокусе? проверяется вводом
    s.cell(row, col)              # ячейка с атрибутами: подсветка фокуса тут
```

Важный момент про оракул. Скрытая каретка сама по себе не баг: при фокусе
на кнопке её и не должно быть. Баг — это когда поле ввода остаётся в
фокусе, а каретки нет. Отличать помогает `types_into_field()`: если после
пропажи каретки ввод всё ещё попадает в поле, значит фокус никуда не
уходил и это действительно баг. Именно по этому признаку в #518 удалось
отделить настоящий дефект от штатного ухода фокуса.

Фиксированные паузы лучше не закладывать: первый запуск с чистым `HOME`
создаёт конфиг и стоит секунд, а последующие — нет. Для всего, что бывает
медленным один раз, есть `wait_for()`.

Клавиши в `ttytest.py` заданы в обычной кодировке терминала. Kitty-протокол
f4 включает только для терминалов, которые ответили на запрос, а наш pty не
отвечает, поэтому разбираться будут именно эти последовательности.
