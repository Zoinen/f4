# Artifactory password bootstrap must use bootstrap.creds

**Date:** 2026-10-06 15:40
**Files:** ci/setup-conan-password-auth.sh
**Severity:** high

## Problem

The password setup helper attempted to change `admin` through
`PUT /access/api/v2/users/admin/password` with a temporary or exchanged access
token. The Artifactory instance authenticated the request but rejected it with
HTTP 403, leaving the password unset.

## Root Cause

The generated bootstrap authorization and the generic tokens created from it
were not accepted by this deployment as the identity required by the user
password endpoint. Adding `api:*` to the token scope did not change the 403.
JFrog provides a separate self-managed recovery mechanism for this case:
Access consumes a `bootstrap.creds` file containing the username and password
during an Access restart.

## Solution

The helper now sends the username and password over SSH stdin, writes the
official `bootstrap.creds` file on the Artifactory host with mode `0600` and
owner `1030:1030`, restarts the container, waits for the local health endpoint
to return successfully, and removes the bootstrap file. Existing identity-token
users retain the direct API path.

## Prevention

- Use the documented `bootstrap.creds` recovery flow when no working identity
  token is available.
- Keep passwords out of command arguments and logs; pass them over stdin.
- Verify both the bootstrap file permissions and Artifactory health before
  reporting success.
- Treat an authenticated `403` as an authorization-path mismatch, not as proof
  that another token scope will work.
