# Stale grouping ranges absorbed the parent entry

**Date:** 2026-09-21 01:38
**Files:** internal/panel/grouping.go; internal/panel/list.go;
internal/panel/file_panel_test.go
**Severity:** high

## Problem

After opening a directory with Group by enabled, the Qt masonry view could
place the `..` parent entry inside the first visible group. In the reported
case the directory had one `No data` group, so the parent tile appeared mixed
with the group's photo tiles instead of appearing before the group separator.

## Root Cause

Directory loading can replace the catalog before the normal sort/group rebuild
runs. The previous grouping snapshot still used the old catalog's ranges, and
the next display-row rebuild interpreted that stale range against the new
entries. A group beginning at index one in the old catalog could therefore
consume the new catalog's parent entry at index zero.

## Solution

Added a grouping-aware catalog sort path for detached and windowed directory
loads, carrying the active grouping settings into the temporary sorter. After
installing a replacement catalog, grouping rows are rebuilt from the current
entries before publication. Metadata batches also re-sort and rebuild once so
entries leaving provisional `No data` classifications cannot leave stale
ranges behind. A completion path with no chunk callback now clears old ranges
as well. Added a regression test covering a phased reload from one catalog to
another and asserting that `..` remains outside the group.

## Prevention

- Treat grouping ranges as catalog-revision data; never reuse them after an
  entry replacement without rebuilding them.
- Keep sorting and grouping together for asynchronous, detached catalog
  paths, including empty/provider-completion paths.
- Add regression coverage that changes both the catalog and the active
  grouping mode, and assert the parent row's exact display position.
