# Multiline command input navigation and pointer interaction

**Date:** 2026-09-23 01:16
**Files:** `internal/cmdline/line.go`, `internal/cmdline/qt_semantic.go`, `internal/panel/frame.go`, `internal/panel/qt_semantic.go`, `third_party/vtui/edit.go`, `qt/host/qml/CommandLineView.qml`, related tests and `docs/TERMINAL.md`
**Severity:** medium

## Problem

At the first or last visual line, Up/Down unexpectedly recalled command history. The Qt input scrolled in response to ordinary caret movement, had no scrollbar for overflow, and lacked pointer selection. Console input gestures did not retain capture for drag/release; a triple-click selected all text instead of the logical line.

## Root Cause

Both the Go input path and Qt shortcut explicitly delegated edge arrows to history. Qt derived its viewport offset unconditionally from the caret instead of maintaining independent scroll state. The Qt mouse overlay only positioned the caret, and the console frame routed command-line mouse events only in one navigation mode and only for the initial press. The edit control treated every triple-click as Select All.

## Solution

Keep multiline edge arrows within the input on both backends. Make Qt scroll position stateful, expose the shared scrollbar, and keep the caret visible only when it leaves the viewport. Map Qt drag, double-click, and triple-click selections back through the display-to-source offset map to the shared Go editor. Capture full console mouse gestures at the command line and select a logical line on multiline triple-click. Add `[FIX:command-line-navigation]` and `[FIX:command-line-selection]` debug logging. Regression checks failed before the changes and passed afterward. The Go and Qt host binaries build; focused Go and Qt suites pass.

## Prevention

Test keyboard navigation at both multiline edges, pointer selection across both backends, and the difference between caret visibility and viewport scrolling. Qt geometry tests must wait for deferred input-height publication before comparing bar heights.
