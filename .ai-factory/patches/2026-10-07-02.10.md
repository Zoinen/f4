# Reduce live video GPU contention without changing resampling quality

**Date:** 2026-10-07 02:10 Europe/Moscow
**Severity:** high
**Files:** `third_party/ZoinGallery/{CMakeLists.txt,ViewerResampleEffect.cpp,ViewerResampleEffect.h,ViewerLinearVideoTexture.cpp,ViewerLinearVideoTexture.h,qml/ViewerResample.qml,resources/viewer_resample.frag,tests/ViewerResampleGpuTest.cpp}`; optimization checklist in `.ai-factory/FIX_PLAN.md`.
**Scope:** application rendering only; cached Qt and FFmpeg binaries unchanged.

## Problem

Playing the supplied 4K clip made the desktop, including the pointer, lag.
The earlier presentation-cache fix removed unnecessary work for paused frames,
but each new video frame still repeated expensive filtering and color conversion.

The original implementation was preserved as an immutable diagnostic reference
before optimizing. Fresh-frame rendering plus synchronous readback took roughly
60 ms. In a separate six-second live capture of the original application,
KWin's GPU-job completion latency reached 88.092 ms at p95, despite otherwise
using hardware OpenGL. This was not evidence that software rendering was needed.

## Root Cause

- At the clip's 3840x2160-to-2560x1440 reduction, the shader evaluated an 8x8
  footprint per output pixel. Exactly zero-weight taps still fetched texels and
  evaluated YUV-to-linear-light conversion. Horizontal coefficients were also
  recomputed inside the vertical loop.
- Neighboring output pixels repeated conversion of the same source pixels.
  Keeping uploaded video planes or the completed paused presentation does not
  remove that repeated work for newly decoded frames.
- The resulting GPU backlog delayed both the application and compositor.
  Aggregate CPU usage alone did not identify this shared-GPU contention.
- A Qt layer texture being allocated is not proof that its conversion draw
  succeeded. Publishing such a texture before verifying the producer could
  display blank or stale frames and would make a performance fix unsafe.

## Solution

Retain the filter kernel, nonzero accumulation order, normalization, linear-light
color conversion, source resolution, orientation, dithering, and final geometry.
No bilinear substitute or quality reduction was introduced.

1. Compute horizontal coefficients once and skip only exactly zero-weight rows
   and taps. Keep the ordinary image material unchanged and retain a separately
   compiled, constructor-selected original video shader for A/B checks.
2. For admitted static downscaling, convert each source pixel once per new frame
   into a full-resolution RGBA32F texture. The same final filter reads that
   full-precision linear data instead of repeatedly converting video planes.
3. Own the conversion render pass in `ViewerLinearVideoTexture`, rather than
   assuming that Qt's generic layer completed successfully. Check texture,
   render target, buffers, bindings, shaders and pipeline creation. Publish
   readiness only after recording the conversion draw into the same command
   buffer as its consumer. This guarantees command ordering, not CPU-visible
   GPU completion, and adds no synchronous readback to production playback.
4. Freeze the converted/direct choice for each final draw. Require matching
   source identity, immutable frame revision, native size and QRhi. If the
   producer is unavailable, failed, unsupported or stale, use the original
   direct YUV path in that same draw.
5. Bound admission before allocation: maximum 4096 pixels per axis, source
   budget 9 Mi pixels, and aggregate active RGBA32F storage of 144 MiB per QRhi.
   This clip uses 126.56 MiB. Retired in-flight resources can temporarily outlive
   the active reservation; the bound is not a claim about total resident GPU
   memory. Release reservations on failure and latch failures until size/RHI
   changes, instead of retrying on every frame.
6. Require supported float render targets, texel fetch, single-sample rendering,
   eligible downscale geometry and unchanged presentation-cache eligibility.
   Motion, fades, fractional/incompatible transforms, nearest/native/magnified
   views, pyramids, oversized sources and unsupported backends retain the
   existing full-quality paths. Preserve the finished RGBA8 presentation cache
   for idle/paused reuse.
7. Keep provider creation/destruction and retained video-frame/QRhi resources on
   the render thread. Handle invalidation and discarded cleanup jobs; clear the
   entire video texture pool on QRhi teardown. Diagnostics are opt-in, with
   bounded `[FIX:viewer-sampling]` warnings for producer failures.

### Fresh-frame benchmarks

Each result uses independent immutable decoded 4K YUV420P frames, a 2560x1440
target at DPR 1.75, three warmups and twenty measured new revisions. Decode and
source-buffer construction are outside the measured interval. Timing includes
scene synchronization, rendering, synchronous GPU readback and copy; it is not
isolated shader execution time. Every measured output matches the original
reference exactly. Reusing a paused frame cannot satisfy this benchmark.

| Configuration | Original median | Optimized median | Ratio |
| --- | ---: | ---: | ---: |
| Zero-weight/invariant optimization only | 56.8568 ms | 40.3019–44.3843 ms | 1.28–1.41x |
| Combined full-precision conversion reuse | 61.1624 ms | 18.6255–21.1383 ms | 2.89–3.28x |

The ranges are separate explicit-reference-off and normal-default runs.
Combined p95: original 74.0547 ms, optimized 21.6771–22.3243 ms. Logs:
`work/video-optimization-final-skip-only.txt` and
`work/video-optimization-final-real-clip.txt`.

### Live desktop benchmark

Same supplied clip, maximized foreground viewer at 67% fit, Wayland hardware
OpenGL, six-second captures. Tracepoints correlate GPU fences with the Qt render
thread and KWin. Run-to-done latencies include hardware queue contention; they
are not isolated execution time, and overlapping job durations must not be
summed as GPU utilization.

| Live GPU-job completion | Original median / p95 | Optimized median / p95 |
| --- | ---: | ---: |
| Qt render thread | 79.462 / 97.636 ms | 11.426 / 11.939 ms |
| KWin compositor | 4.758 / 88.092 ms | 1.168 / 2.602 ms |

Final probes counted **180 accepted frames, 180 completed conversion
submissions, 180 final filters** in six seconds: approximately 30 fps, matching
the source's 29.97 fps. After pausing and settling, a three-second trace counted
**zero accepted frames, zero conversions, zero final filters**, with no Qt GPU
jobs attributed by the helper. KWin p95 was 2.002 ms while paused.

Evidence: `work/video-live-{original,optimized}-gpu-stats.txt`,
`work/video-live-optimized-cadence.txt`,
`work/video-final-paused-{gpu-stats,cadence}.txt`. CPU utilization was not lower
in the faster live capture, which processed more work/cadence; do not advertise
this as a CPU optimization. GPU memory is not represented by process RSS.

## Prevention

- Establish an immutable original render path and an executable fresh-frame
  benchmark before changing video math. Compare complete rendered pixels, not
  merely screenshots by eye or metadata/position events.
- Check both isolated work and live shared-GPU contention. Count accepted,
  converted and filtered revisions separately, and measure paused idle behavior.
- Publish optional GPU intermediates only after a checked producer submission;
  allocation, format support, and a Qt texture-provider pointer are not enough.
- Reserve aggregate resources before enabling hidden allocation. Validate
  source/revision/RHI lifetime and same-draw fallback; inject failure paths.
- Keep diagnostics disabled by default. Do not rebuild dependency toolchains or
  lower quality to hide an application-level resampling bottleneck.
- Additional coverage: repeat pixel-exact, allocation-failure and context-reset
  tests on Vulkan, Windows/D3D and macOS/Metal, and stress simultaneous viewers
  plus resize/seek/close-reopen on memory-constrained devices.
