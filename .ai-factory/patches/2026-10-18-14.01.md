# Preserve contributor highlighting behavior through unified migration

**Date:** 2026-10-18 14:01 UTC
**Files:** internal/filegroups/match.go, match_windows.go, store.go,
document_help.go, highlight.help.ini; internal/panel/file_groups_highlight_test.go
**Severity:** medium

## Problem

The new file-group matcher dropped Junction appearance on non-Windows hosts
even when the VFS supplied its reparse tag. The replacement startup loader also
stopped refreshing the generated highlight.ini documentation.

## Root Cause

Junction classification was mistaken for a host-OS permission attribute and
placed only in match_windows.go. Existing upstream tests continued to exercise
the legacy loader, so they passed while the new migration path differed.
Removing startup writes was intentional, but no transactional replacement for
generated help was introduced.

## Solution

Classify Junction using vfs.LinkKindOf in the shared matcher. Add a migration
parity regression covering all four colour states, markers and tree rows for
ordinary, hidden, symlink and junction folders. Refresh a marked, embedded help
block only in Commit, before atomic publication. Preserve personal comments,
unmarked legacy help, BOM and unknown sections. Refuse malformed managed markers
rather than risk deleting user text. Opt-in diagnostics use [FIX:file-groups]
at compile/save boundaries, never per painted entry.

## Prevention

Exercise existing behavior through the new adapter/migration path, not only its
legacy implementation. Keep VFS metadata classification independent of the host
platform. Moving a startup side effect into a transaction requires explicit
Apply/Cancel/failure coverage. Tests must cover documentation refresh idempotence,
unknown data preservation and non-writing reads.

## Verification

Before the fix the parity test failed for all four Junction colour states,
the marker and normal/cursor tree rows. The Apply regression failed because
help was absent or stale. The exact same tests pass after the fix. Related
filegroups/theme/settings/config suites, the full short panel/app suites,
go vet and the Go build pass with CGO_ENABLED=0. Windows amd64 test compilation
passes; no native Windows runtime check was performed. The isolated Qt host
started and opened Settings with the new Go binary.
