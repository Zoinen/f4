# Video thumbnail cancellation during folder navigation

**Date:** 2026-09-21 01:17
**Files:** third_party/ZoinGallery/DecodeManager.h; third_party/ZoinGallery/DecodeManager.cpp; third_party/ZoinGallery/Runners/VideoThumbnailRunner.cpp; third_party/ZoinGallery/MasonryLayoutThumbnails.cpp; third_party/ZoinGallery/tests/DecodeLifecycleTest.cpp
**Severity:** high

## Problem

Holding Enter while entering and leaving a folder containing many large local videos made navigation feel slow. Video thumbnail workers continued running after the catalog had changed, competing with the next navigation and repeatedly starting work that would be discarded.

## Root Cause

`Runner::cancel()` published an atomic flag and cancelled the source, but `VideoThumbnailRunner` was waiting in a nested `QEventLoop` owned by its decode worker. No event reached that loop, so the worker stayed occupied until a frame or media timeout woke it. Visible video requests also entered the urgent decode lane, so a folder transition could start several expensive Qt Multimedia/FFmpeg opens before cancellation.

## Solution

Added a queued `Runner::cancelRequested` signal. `VideoThumbnailRunner` connects it to a worker-thread cancellation callback that stops the player, quits the nested loop, and emits opt-in `[FIX:video-cancel-wake]` timing events. Visible video thumbnail requests now use the background decode lane, leaving urgent workers for catalog metadata and navigation. Added a lifecycle regression test proving that a nested runner exits promptly after cancellation.

## Prevention

- Any runner that owns a nested event loop must connect cancellation to a queued wake-up in that loop.
- Keep platform multimedia work out of navigation-critical priority lanes.
- Retain navigation benchmarks with media timing enabled for folders containing large H.264/AV1 files.
- Keep a regression test that measures cancellation-to-finished latency.
