# Cap the reusable panel thumbnail cache slot

**Date:** 2026-11-04 17:00
**Files:** third_party/ZoinGallery/PersistentDerivedImageCache.cpp, Runners/ImageDecodeRunner.cpp, src/embed/DecodeSizePolicy.*, src/embed/ThumbnailMemoryCache.cpp, cache tests, docs/FILE_FIELDS.md
**Severity:** medium

## Problem

Changing the requested thumbnail size could leave several files for the same
source revision, and the reusable entry could grow beyond 1024 pixels.

## Root Cause

The reusable slot fell back to a size-specific write when a candidate did not
replace the current frame or when the slot was busy. Read and encode decisions
did not treat a maximum-size frame as satisfying subsequent larger requests.

## Solution

Use one atomic write destination for each thumbnail revision and transform.
Compare actual frame dimensions before WebP encoding and again on commit.
Scale frames to at most 1024 pixels on the long edge and let both disk and
memory cache hits satisfy larger requests once that size is available. Preserve
read-only access to historical size-specific entries under normal eviction.

## Prevention

Exercise different request sizes, stale completions, both orientations, and
the source-read gate. Verify that there is one thumbnail file and that its
bytes remain identical after a later oversized request.
