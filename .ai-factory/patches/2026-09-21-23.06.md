# Masonry keyboard navigation crossing grouped headers

**Date:** 2026-09-21 23:06
**Files:** third_party/ZoinGallery/qml/GalleryNavigationController.qml; third_party/ZoinGallery/tests/MasonryLayoutModesTest.cpp
**Severity:** medium

## Problem

In grouped Masonry mode, pressing Up or Down from an item adjacent to a group
header could leave the keyboard cursor on the same item. The spatial hit test
correctly returned no file index for the header, but navigation did not advance
to the first file in the next group or the last file in the previous group.

## Root Cause

Masonry vertical navigation uses a QML spatial probe. When the probe landed in
the header gap, its fallback called the inclusive `visibleNavigationIndex`
helper with the current source index. That helper intentionally returned the
current index for an inclusive query, so the fallback converted a missing hit
into a self-loop instead of a strict adjacent visible file.

## Solution

The fallback now asks the native visibility index for the strict next visible
source index in the requested direction and keeps the current index only when
the catalog boundary has been reached. Cross-group fallback decisions emit an
opt-in benchmark trace with the `[FIX:group-header-navigation]` marker.

A regression test exercises the actual QML navigation function in both
directions across a Masonry group separator and verifies that the header is not
treated as a file row.

## Prevention

- Keep inclusive navigation helpers separate from strict neighbor lookups.
- Test keyboard navigation across every virtual layout element, including
  grouped headers and collapsed sections.
- Retain the grouped Masonry regression when changing cursor reveal or spatial
  hit-testing code.
