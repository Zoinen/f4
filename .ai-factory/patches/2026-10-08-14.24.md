# Repair an incompatible ARM64 dependency without rebuilding Qt or FFmpeg

**Date:** 2026-10-08 14:24 MSK
**Files:** `.github/workflows/build.yml`, `ci/build-portable-qt-linux.sh`,
`ci/test_portable_qt_linux.py`
**Severity:** high

## Problem

The Linux Qt release workflow failed on ARM64 before configuring the host:
`trusted baseline contains an ARM64 libffi archive incompatible with glibc 2.27`.
The restored Conan cache contained `libffi.a` referencing newer glibc symbols.
The release lane trusted the graph and selected `--build=never`, so the
baseline scanner correctly stopped instead of repairing the incompatible
archive.

## Root Cause

The normal Zoin branch build enables multimedia bootstrap mode and scans known
ARM64 static archives for newer-glibc symbols. The dedicated manual release
lane did not enable that mode, so it treated a cached package as an audited
binary-only baseline. Conan package IDs do not encode the glibc build baseline,
which let the invalid archive appear compatible until the host check.

## Solution

Make the dedicated release lane run the existing baseline repair scanner and
pass a release-only binary guard into the Ubuntu 18.04 build container. In that
mode Conan may rebuild missing or incompatible non-multimedia dependencies, but
excludes `qt/*` and `ffmpeg/*` from all missing-binary source builds. The
required Qt and FFmpeg binaries must come from Artifactory or the install fails.
The regression test covers the workflow flags and the exact Conan exclusions.

## Prevention

- Treat restored Conan caches as candidates, not as proof of the libc baseline.
- Keep the ARM64 static-archive scan in every release path that restores the
  package cache.
- When a release forbids rebuilding a dependency, express it as a Conan build
  exclusion so a missing binary fails instead of silently compiling it.
- Test release-specific workflow environment and build policy alongside the
  archive scanner.
