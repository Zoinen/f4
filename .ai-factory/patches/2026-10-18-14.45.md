# Forward buttonless Qt console hover

**Date:** 2026-10-18 14:45 UTC
**Files:** qt/host/src/VtuiGridItem.cpp, qt/host/src/VtuiGridItem.h,
qt/host/tests/F4GalleryPointerTests.cpp, qt/host/README.md
**Severity:** medium

## Problem

In Shift+F12 console presentation, hovering over Settings controls did not
update their hover help. Clicks and drag motion still worked.

## Root Cause

The grid enabled Qt Quick hover events but implemented only mouseMoveEvent.
Buttonless movement arrives as QHoverEvent, which never reached the existing
Go input protocol. Existing pointer tests exercised clicks, wheel and dragging,
not the unpressed Qt event path.

## Solution

Forward HoverEnter/HoverMove as mouse-moved packets with zero buttons and
down=false, retaining cell mapping and modifiers. Respect pointerInputEnabled
and ignore hover during a native drag so the original mouse path remains sole
owner. Do not force keyboard focus. Keep all production changes in Qt; the Go
protocol and upstream console implementation are unchanged. Optional host input
tracing uses F4_TRACE_GRID_INPUT and [FIX:qt-grid-hover].

## Verification

The new wire-level test failed before the fix with no mouse packet. It passes
afterward, covering enter, move, modifiers, coordinates, focus, semantic-mode
gating and suppression during dragging. Related console pointer, IME, key-repeat
and focus tests pass at 175% scale (7 test functions including init/cleanup).
The Qt host builds successfully and the application is restarted with it.

## Prevention

Test hover as its own input event, not a mouse move with a pressed button.
Real windows may emit legitimate hover packets before clicks; validate their
flags and buttonless state instead of assuming every first packet is a press.
Useful additional coverage is native-platform hover while toggling presentation
with a stationary pointer over an already open Settings dialog.
