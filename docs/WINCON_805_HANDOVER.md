# Issue #805 — картинки в консольном f4 на Windows: что установлено, что нет, что делать

Дата: 2026-08-27. Исследование по коду f4 (`0eda4343`), vtui (`4bdf763`),
исходникам microsoft/terminal (main), логу `debug.log` из тикета и парным
логам `f4probe 5` под classic conhost / Windows Terminal.
Формат: сначала факты с источниками, потом открытые вопросы, потом
инструкция исполнителю (для модели послабее — шаги маленькие, проверяемые),
в конце — памятка для пользователей по сбору информации.

## 1. Установлено точно

**F1. В тикете три разных ситуации, и у них разные причины.**
- (a) Windows Terminal, f4 запущен *напрямую* (ярлык на `f4.exe`, Win11 с WT
  как терминалом по умолчанию) — картинки нет / «мелькает и накрывается».
- (b) Windows Terminal через `wt.exe f4.exe` — работает (Zeroes1, tarlabnor).
- (c) Классический conhost (cmd.exe в своём окне, Win10) — чёрный прямоугольник,
  клин, 17 % CPU; на свежих сборках — «картинка на мгновение мелькает и исчезает».

**F2. Под Windows Terminal `GetConsoleWindow()` возвращает *видимое* окно.**
Это псевдо-окно ConPTY: класс `PseudoConsoleWindow`, `WS_POPUP`,
`WS_EX_TOOLWINDOW|WS_EX_NOACTIVATE`, размер 0×0, владелец — окно WT
(через `GWLP_HWNDPARENT`). Когда вкладка видна, OpenConsole делает ему
`ShowWindow(SW_SHOWNOACTIVATE)`, когда скрыта — `SW_MINIMIZE`; в обоих
случаях `IsWindowVisible` = TRUE (WS_VISIBLE не снимается).
Источник: `src/interactivity/base/InteractivityFactory.cpp`
(`CreatePseudoWindow`, `SetVisibility`), GH#12515, GH#13066.
**Следствие: `wincon.ConsoleWindow()` (проверка `IsWindowVisible`) считает WT
«настоящей консолью». Утверждение в `WINCON.md` §1 («под WT окно никогда не
показывается, IsWindowVisible false») — неверно.**

**F3. При запуске через «терминал по умолчанию» WT *не* ставит `WT_SESSION`.**
Окружение процесса задаёт тот, кто его запустил (Explorer); WT подключается
позже через handoff и в чужой environment ничего не пишет. Открытый запрос:
microsoft/terminal#13006. Через `wt.exe f4.exe` переменная есть.
**Следствие для (a):** нет `WT_SESSION` → `DetectGraphicsProtocol` даёт
`GraphicsNone` → `InstallConsoleOverlay` → `ConsoleWindow()` доверяет
псевдо-окну (F2) → оверлей создаётся как child окна 0×0 → `ClientSize()`
= 0×0 → каждый кадр уходит в `hide("nothing on the client area")`.
Картинка «поддерживается» (протокол External), но рисовать её некуда;
вьюер держит под неё пустую область. Это ровно случай tarlabnor.

**F4. vtui умеет спросить терминал напрямую (DA1), но f4 этим не пользуется.**
`vtui.ProbeGraphicsProtocols()` (`graphics_probe.go`, Windows-реализация в
`graphics_probe_windows.go`) шлёт `ESC [ c` и ищет параметр `4` (sixel).
`git log -S ProbeGraphicsProtocols` в f4 — пусто: вызова нет ни на одной
платформе. Актуальный код terminal отвечает `?61;4;6;7;14;21;22;23;24;28;32;42[;52]c`
(`adaptDispatch.cpp: DeviceAttributes`), т.е. WT (при любом способе запуска)
и OpenConsole/новый conhost объявляют sixel; старый conhost Win10 — нет.

**F5. Кодировщик sixel в vtui уже готов к WT без `WT_SESSION`.**
`isWindowsSixelHost` (`graphics_sixel.go:284`): `WT_SESSION` *или*
`GOOS==windows && !WezTerm` → слои по 255 цветов и виртуальная клетка 10×20.
Значит для (a) достаточно правильно выбрать протокол; vtui менять не нужно.

**F6. Окно conhost рисует *поверх* своих child-окон.** Стили окна консоли:
`WS_OVERLAPPEDWINDOW|WS_HSCROLL|WS_VSCROLL`, ex: `WS_EX_WINDOWEDGE|WS_EX_ACCEPTFILES|
WS_EX_APPWINDOW|WS_EX_LAYERED` (`src/interactivity/win32/window.cpp`,
`CONSOLE_WINDOW_FLAGS`). **`WS_CLIPCHILDREN` нет.** Любая перерисовка conhost
(текст f4, мигание курсора) затирает пиксели нашего child-окна, и никто его
после этого не инвалидирует. Это и есть «мелькает и исчезает» в (c):
окно показали и нарисовали (после d801c6d — в одном пробуждении), следующий
BitBlt консоли его закрасил.

**F7. Cross-process parent/child *и* owner/owned окна сцепляют очереди ввода
(implicit AttachThreadInput), транзитивно.** Raymond Chen, 2013-04-12
(«Is it legal to have a cross-process parent/child or owner/owned window
relationship?») и 2011-03-31. Значит «сделать оверлей owned-окном консоли»
не спасает — только окно *без* parent и *без* owner.

**F8. Лог Zeroes1 (Win10 19045, conhost, сборка ac048ed 2026-08-25 14:49):**
```
16:22:24.741 WINCON: overlay ready over the console window   (cell 12x28)
16:22:45.021 IMAGE_GEOM: console=120x30 ... img=1100x578 place=0,1 120x28
16:22:45.070 WINCON: frame 1440x784 at 0,28, 1 piece(s)
16:22:45.070 WINCON: 20.3s frames=2 new=1 scale=32ms/32ms window=7ms
             pump=0 move=0 rgn=0 inval=0 paint=0 blank=0 gaveup=1(no placements)
16:22:45.076 FM: renderPhase() ...   <- последняя строка лога, дальше 30 с тишины
```
Масштабирование 32 мс — не оно. Запрос ушёл на pump-поток, и через ~5 мс
f4 встал целиком в следующем `renderPhase` (до первого WINCON-лога кадра, т.е.
скорее всего на записи кадра в консоль). Это картина взаимной блокировки
conhost ↔ pump-поток (F7) при первом `SetWindowPos(SWP_SHOWWINDOW)`/`WM_PAINT`
child-окна, при которой conhost перестаёт обслуживать и вывод, и ввод f4.
`pump=0` в строке — снимок на момент flush, сам по себе не доказательство;
доказательство — обрыв лога.

**F9. Побочное:** `cmd/f4/window_icon_windows.go` делает синхронный
`SendMessageW(WM_SETICON)` в окно консоли из произвольной горутины —
ещё одна точка, где f4 повиснет, если conhost заклинило. Под WT это
уходит в псевдо-окно и безвредно.

**F10. Манифест f4.exe объявляет `permonitorv2`** (`rsrc_windows_*.syso`) —
координаты окон в физических пикселях, пересчётов DPI не нужно.

**F11. Новый ConPTY (VtIo, terminal main) пропускает вывод клиента в терминал
насквозь; VT-рендерер (`src/renderer/vt`) удалён.** Поэтому sixel из f4
доходит до WT. Оборотная сторона: под другими ConPTY-хостами (VS Code и т.п.)
ответ на DA1 может по-прежнему обещать sixel — это уже сегодняшнее поведение
для `wt.exe`/`WT_SESSION`, новой проблемой не является, но записать стоит.

**F13. Замер на 10.0.22000.2538, классический conhost** (`f4probe`, тикет #425;
запуск ярлыком из Explorer, `WT_SESSION` не задан):
- `DA1` → `ESC[?1;0c`. Sixel **не заявлен** — этот conhost картинки не рисует,
  оверлей здесь нужен. `DA2` → `ESC[>0;10;1c`. На `XTVERSION` (`ESC[>q`) и на
  запросы sixel-геометрии (`ESC[?1;1;0S`, `ESC[?2;1;0S`) ответа нет вообще.
- Окно `GetConsoleWindow`: класс `ConsoleWindowClass`, видимое, клиентская
  область 960×480, owner и `GWLP_HWNDPARENT` нулевые. То есть проверка из шага 1
  на этой сборке даёт «доверять можно», как и задумано.
- `WS_CLIPCHILDREN` отсутствует — **F6 подтверждён на второй сборке**, а не
  выведен из исходников.
- В `exstyle` окна консоли есть `WS_EX_LAYERED` (0x00080000). Наш оверлей по
  шагу 3 тоже layered; на поведение `UpdateLayeredWindow` для *нашего* окна это
  не влияет, но знать об этом стоит до того, как кто-то удивится.
- `GetConsoleProcessList` видит только сам процесс; conhost — ребёнок процесса,
  создавшего псевдоконсоль, а не ребёнок шелла.

**F14. Парный замер на той же 10.0.22000.2538 под Windows Terminal**
подтвердил обе ветки определения хоста:
- conhost: `ConsoleWindowClass`, видимая клиентская область 960x480,
  `WS_CLIPCHILDREN` нет, DA1 `ESC[?1;0c` без sixel;
- WT: `PseudoConsoleWindow`, формально видимое окно 0x0, owner класса
  `CASCADIA_HOSTING_WINDOW_CLASS`, `WT_SESSION` задан, DA1
  `ESC[?61;4;6;7;14;21;22;23;24;28;32;42;52c` с sixel.

DA2 в обоих случаях одинаков (`ESC[>0;10;1c`), XTVERSION и оба запроса
sixel-геометрии остались без ответа. Значит положительный параметр 4 в DA1
достаточен сам по себе; молчание XTSMGRAPHICS его не отменяет. Весь
cursor-model / resize / oracle раздел отдельной скрытой ConPTY, которую
создаёт пробник, совпал между хостами байт-в-байт, а семантические результаты
cmd совпали (один ECHO-on transcript отличался эквивалентной раскладкой
CRLF/cursor). Разница относится к возможностям внешнего терминала f4, а не к
измеренному поведению дочерней ConPTY.

Это был обычный запуск из вкладки WT с `WT_SESSION`, не handoff приложения,
запущенного ярлыком. Поэтому F2 и ответ DA1 от WT измерены, но случай (a) из
F1 без `WT_SESSION` по-прежнему требует прикладного лога.

**F15. Автоматический прогон `f4probe 6` на той же 22000.2538** подтвердил
forced-conhost и явный WT. Запуск с очищенными WT-маркерами выбрал классический
conhost: значения default-terminal delegation в реестре не заданы. В этом
дочернем запуске стандартные handles оказались перенаправлены, поэтому
отсутствие DA1 не является ответом терминала; классификация следует из
`ConsoleWindowClass` и цепочки процессов. Реальная матрица f4 прошла механику
всех четырёх reflow-режимов, но старый итог `complete` был слишком широким:
все oracle/probe passes завершились `nothing stamped` из-за неверного
сопоставления ConPTY viewport с viewport f4. Это исправлено сопоставлением с
объединённым локальным журналом истории и экрана; к графическому overlay этот
matcher не относится.

**F16. `CSI 16 t` под WT возвращает виртуальную клетку sixel, а не шрифт.**
Замер `f4probe 1.1` под Windows Terminal на 22000: `ESC[6;20;10t` (20×10) при
`CSI 14 t` → `ESC[4;600;1200t`, то есть 600×1200 px на 120×30 клеток — те же
10×20. Совпадает с допущением `isWindowsSixelHost` в vtui (F5): менять vtui
не нужно, но и трактовать этот ответ как размер шрифта нельзя.

**F17. `GetCurrentConsoleFontEx` под ConPTY врёт: ширина клетки = 0.**
Тот же замер: под WT «character cell: 0x16 pixels», под классическим conhost
на той же машине — честные 8×16. Любой расчёт геометрии картинки, делящий на
ширину клетки из Win32 Console API, под ConPTY даст деление на ноль или
бессмыслицу. **Правило: под ConPTY размер клетки брать только из `CSI 16 t`**
(см. шаг 3a).

**F12. PictureView для Far Manager: что известно косвенно.** Исходники
плагина непубличны; по журналу изменений ConEmu видно следующее.
ConEmu перехватывает `GetConsoleWindow`, а также `GetParent`, `GetWindow` и
`GetAncestor`, подставляя своё окно отрисовки — значит PicView берёт HWND
консоли и лезет по иерархии вверх (раньше для него требовался отдельный
враппер). ConEmu приходилось *специально прятать* окно PicView при
переключении вкладок («Не скрывался PictureView на Win7 при переходе по
вкладкам») — то есть окно PicView живёт своей жизнью, а не отсекается
автоматически как child. И: «при просмотре картинок (PicView и т.п.) временно
отключается альфа-прозрачность» — с layered-окном хоста PicView уживается
плохо. Вывод для нас: **повторять схему PicView один в один не нужно** —
она рабочая ровно там, где хост знает её в лицо. Шаг 3 (собственное
layered-окно, которое само следит за консолью и само прячется) покрывает те
же случаи без помощи со стороны хоста.

**F18. Sixel под WT на 22000 не просто заявлен — он нарисовался.**
Отдельный пользовательский пробник (`f4probe 1.1`, отчёты в тикете) показал
тестовый квадрат: под Windows Terminal пользователь подтвердил «цвета
появились», под классическим conhost той же машины — «ничего не появилось».
Это ожидаемо (conhost sixel и не заявляет, для него и придуман оверлей), но
теперь ветка (b) подтверждена не только положительным DA1, а картинкой на
экране. Пропорции квадрата остались непроверенными: вопрос был задан, ответа
в отчёте нет.

**F19. Молчание XTSMGRAPHICS в `f4probe 1.1` — не находка, а опечатка.**
Тот пробник шлёт запрос геометрии как `ESC[?2;1;S`, без обязательного нуля;
правильная форма `ESC[?2;1;0S`. Поэтому «no answer» в его отчётах ничего не
доказывает. В `tools/conptyprobe` форма правильная, и там WT на этой сборке
действительно молчит (F14) — вот это и есть измерение.

**F20. Правило выбора размера клетки (F16/F17) вынесено в код.**
`tools/conptyprobe/graphics_geometry.go`: сначала `CSI 16 t`, затем вывод из
`CSI 14 t` / `CSI 18 t`, и только для настоящего `ConsoleWindowClass` —
`GetCurrentConsoleFontEx`. Любой источник с неположительным измерением
отбрасывается, а не делится. Тесты закрывают обе снятые конфигурации: WT
(`ESC[6;20;10t` против нулевой ширины из Win32) и conhost (молчание плюс
честные 8×16). Шаг 3a теперь имеет готовую реализацию для переноса в f4.

**F21. Обе жалобы — одна форма: поверх картинки что-то перерисовывается.**
В conhost это перерисовка окна консоли поверх child-окна (F6), в Windows
Terminal — запись текста в те же ячейки, где живёт sixel. Отсюда пробник
`tools/f4imgprobe`: он не обследует машину, а прогоняет каждый механизм
показа картинки через события, подозреваемые в затирании, и спрашивает
пользователя, уцелела ли она. Для conhost — один и тот же квадрат как
child-окно (сегодняшний f4) и как top-level layered-окно (шаг 3), с
принудительной перерисовкой консоли под обоими; плюс замер
`SendMessageTimeout` к окну консоли, чтобы заклин (F8) стал числом, а не
зависанием. Для WT — sixel, а затем по одному: текст в стороне, `ESC[K` по
строкам самой картинки, прокрутка, альтернативный экран, двадцать
перерисовок подряд, ресайз окна. «Иногда работает» после такого прогона
превращается в список событий, каждое из которых либо стирает картинку,
либо нет. Отчёт пишется на диск после каждой строки.

**F22. F6 на 22000 не воспроизвёлся, а F7 воспроизвёлся. Это меняет
обоснование шага 3.** Полевой прогон `f4imgprobe` в классическом conhost на
10.0.22000: child-окно консоли показало квадрат, и перерисовка текста под ним
**не повредила картинку** — «появился и остался целым». Зато пока child-окно
существовало, консоль **перестала принимать клавиши и мышь**; после его
уничтожения ввод вернулся. Повторено дважды, слово в слово. То есть на этой
сборке жалоба «мелькает, клин, 17% CPU» — это F7/F8 (сцепка очередей ввода),
а не затирание. F6 остаётся
верным по исходникам и по отсутствию `WS_CLIPCHILDREN` (F13), но как *причина*
жалобы он на 22000 не подтверждён. **Шаг 3 обоснован F7, а не F6** — и это
важнее, потому что F7 нельзя обойти ни перерисовкой, ни инвалидацией.

**F23. Layered-окно шага 3 проверено на машине и работает** (два независимых
прогона, второй — с исправленным пробником). Тот же прогон:
top-level `WS_EX_LAYERED|WS_EX_TRANSPARENT|WS_EX_TOOLWINDOW|WS_EX_NOACTIVATE`
без parent и owner создалось, `UpdateLayeredWindow` с премультиплицированным
BGRA прошёл, окно встало ровно над консолью (`GW_HWNDPREV` консоли равен
нашему HWND), синий квадрат виден, перерисовку консоли пережил целиком, ввод
не заморозил. Спецификация шага 3 подтверждена на реальной сборке, а не только выведена.
Повторный прогон добавил последний недостающий кусок: без трекера окно
остаётся на месте при перемещении консоли (Q9), то есть пункт 4 шага 3 —
не перестраховка, а условие работоспособности.

**F24. Sixel в WT привязан к текстовому буферу; убивает его только прокрутка,
зато любая.** Два полевых прогона под WT 1.24.2607.10001 (исправленный прогон
уточняет первый). Картинка не боится ничего из того, что делает f4 кадр за
кадром: альтернативный экран — переживает, двадцать перерисовок подряд —
«steady, no visible change», `ESC[K` **сам по себе** её не стирает.

Уточнение, ради которого стоило перепрогнать: пункты «текст в стороне» и
`ESC[K` в исправленном прогоне дали не «цела» и не «стёрта», а **«уехала вверх
за верхнюю границу и там обрезалась»**. То есть эти шаги ничего не стирали —
они вызывали прокрутку, и картинка уезжала вместе со строками. В первом
прогоне те же шаги дали «цела» просто потому, что прокрутки тогда не
случилось. Прокрутка на три строки уносит картинку совсем, ресайз окна — тоже.

Итог: sixel в WT живёт в текстовом буфере и ездит вместе с ним. **Единственное
правило для f4: перерисовывать картинку после любой прокрутки и после ресайза**
— причём прокруткой считается и обычный вывод строки внизу экрана, а не только
явный скролл. Ничего похожего на «то показывается, то нет» при этом не
наблюдалось, значит исходная жалоба объясняется случаем (a) (нет `WT_SESSION`
→ протокол не выбран), а не потерей уже нарисованного.

**F24a. Форма подтверждена после исправления пробника.** В том же прогоне с
корректным `ESC P 7;0;0 q` тестер ответил «red on the left, blue on the right,
and it looks square». Масштабирования нет: WT рисует sixel пиксель в пиксель,
и виртуальная клетка 10×20 из `CSI 16 t` (F16) — это именно то, подо что
кодировщик vtui уже настроен (F5). Никаких искажений на этом хосте нет.

**F25. «Картинка не квадратная» была дефектом пробника, не терминала.**
Тестовое изображение слалось как `ESC P q` без параметров, а умолчание DCS —
соотношение сторон пикселя 2:1, поэтому WT рисовал его вдвое выше. Правильно
`ESC P 7;0;0 q` (1:1); исправлено. Записано, чтобы никто не искал здесь
искажения масштабирования: их не было. F16/F17 подтверждены повторно
(`ESC[6;20;10t`, `600×1200` на `30×120`, Win32 отдаёт нулевую ширину).

**F26. Замер зависания консоли изнутри своего же процесса невозможен.**
Первая версия пробника слала консоли `SendMessageTimeoutW` и сообщала
«ответила за 0 мс», пока тестер не мог напечатать ни символа. Причина ровно в
F7: сцеплен именно тот поток, который шлёт сообщение. Автоматическая проверка
убрана; свидетельство о заморозке даёт только человек. То же ограничение
касается любой будущей самодиагностики f4 — «pump занят» (шаг 4) видно из
лога, а «conhost не принимает ввод» — нет.

**F27. Половина для Windows Terminal реализована; conhost ждёт шага 3.**
Шаги 1 и 2 в коде. Вместе они закрывают случай (a) вслепую, ровно как обещал
§2a: под WT (любой способ запуска) класс окна — `PseudoConsoleWindow`, оверлей
отклоняется, DA1 отвечает параметром `4`, выбирается sixel; под conhost 22000
класс `ConsoleWindowClass` и DA1 без `4`, поэтому остаётся оверлей — тот самый,
который сегодня морозит ввод (F22) и который переделывает шаг 3. То есть после
этих двух шагов Windows Terminal показывает картинки при любом запуске, а
поведение conhost не изменилось ни в лучшую, ни в худшую сторону.
Не сделано и остаётся отдельной работой: перерисовка картинки после прокрутки
и ресайза, которой требует F24.

## 3. Инструкция исполнителю (патч f4, по шагам)

Общее: Go, только `syscall.NewLazyDLL`/`golang.org/x/sys/windows`, как в

### Шаг 1. Не доверять псевдо-окну ConPTY (чинит случай (a) наполовину)
**Сделано.** `ClassifyConsoleWindow(class, visible)` в `internal/wincon/geometry.go`
(чистая функция, тесты в `wincon_test.go`), `ConsoleWindow()` читает класс через
`GetClassNameW`. Новое значение `SourcePseudo`, `Trusted()` = false, незнакомый
класс тоже не доверяется. Ключевой момент, из-за которого проверки видимости не
хватало: псевдо-окно отвечает «видимое» (F2), поэтому решает класс, а не
видимость.

Файл `internal/wincon/overlay_windows.go`, функция `ConsoleWindow()`:
1. Добавить `procGetClassNameW = user32.NewProc("GetClassNameW")`.
2. После `GetConsoleWindow` прочитать имя класса (буфер 64 uint16).
3. Решение вынести в чистую функцию в `geometry.go`:
   ```go
   func classifyConsoleWindow(class string, visible bool) Source {
       switch class {
       case "PseudoConsoleWindow": return SourcePseudo // новое значение
       case "ConsoleWindowClass":  if visible { return SourceConsole }; return SourceHidden
       }
       return SourceHidden // незнакомый класс не заслуживает доверия
   }
   ```
   `SourcePseudo.Trusted()` = false, `String()` = "a ConPTY pseudo console
   window (Windows Terminal or another terminal on the far side of a pty)".
4. Тесты в `wincon_test.go`: три класса × visible true/false.
5. В `sharedConsoleOverlay` лог уже есть (`WINCON: not drawing over %v`);
   добавить в него имя класса: `WINCON: console window class=%q visible=%v`.
Проверка: под WT при прямом запуске в логе `not drawing over a ConPTY
pseudo console window`, оверлей не создаётся.

### Шаг 2. Спросить терминал через DA1, если окружение молчит (вторая половина (a))
**Сделано.** Решение «спрашивать ли» — чистая функция `shouldProbeGraphics`
(`cmd/f4/graphics_probe_decision.go`, тесты рядом): спрашиваем только если
протокол ещё не выбран, `VTUI_GRAPHICS` пуст, бэкенд не `winapi`/`win32` и это
Windows. Сам вызов — `probeGraphicsIfUnknown` в
`cmd/f4/graphics_probe_windows.go`, подключён в `ManageSessions` после
`PrepareTerminal` и до `InstallConsoleOverlay` и `vtinput.NewReader` (иначе
ответ терминала съел бы читатель ввода).
Подход подтверждён замерами (F13, F14) — WT отвечает `4`, conhost 22000
отвечает `?1;0c`. Различение работает, ложных срабатываний в обе стороны нет.

Файл `cmd/f4/session_windows.go`, в `ManageSessions` **после**
`PrepareTerminal` (VT-вывод уже включён) и **до** `InstallConsoleOverlay`
и `vtinput.NewReader`:
```go
probeGraphicsIfUnknown(scr)
```
Новая функция (файл `cmd/f4/graphics_probe_windows.go`, tag windows;
чистую часть решения — «зондировать ли» — в файл без тега с тестом):
- условия: `scr.Graphics().Protocol() == vtui.GraphicsNone`,
  бэкенд VT (`SelectedTTYBackend` не `winapi`/`win32`),
  `os.Getenv("VTUI_GRAPHICS") == ""` (явный выбор пользователя не трогать);
- вызов `prots := vtui.ProbeGraphicsProtocols()`; если `len(prots) > 0` →
  `scr.Graphics().SetProtocol(prots[0])` и
  `vtui.DebugLog("GRAPHICS: the terminal answered DA1 with sixel; using %v", prots[0])`;
  иначе `vtui.DebugLog("GRAPHICS: DA1 did not declare sixel")`.
- `InstallConsoleOverlay` после этого сам вернётся рано (протокол ≠ None).
Ожидаемое поведение: (a) → sixel (как в (b)); Win10 conhost → протокол
остаётся None → оверлей (шаг 1 разрешает: класс `ConsoleWindowClass`).
Побочный эффект F11 записать в `IMAGES_PLAN.md` как принятое решение.
Опционально в vtui: `da1Sixel` логировать сырой ответ под `VTUI_DEBUG`
(закрывает Q4 логами пользователей).

### Шаг 3. Переделать оверлей conhost: не child, а отдельное layered-окно (чинит (c))
**Сделано** (`internal/wincon/overlay_windows.go`; чистая часть — премультипликация
и `trackStep` — в `layered.go` с тестами). Пункты 1–7 спецификации реализованы
как написано; пункт 4 — таймером, без `SetWinEventHook` (улучшение отложено до
полевой проверки таймера). Пункт 8 — `WINCON.md` §1–2 переписаны. Не проверено
на живом f4: сворачивание, перекрытие другими окнами, смена foreground (Q6, Q7)
— это первое, что должен сказать полевой прогон.
Статус механизма: проверен на 22000 (F23). Обоснование — F7, а не F6: на этой
сборке child-окно картинку не теряло, но морозило ввод консоли (F22).
Главный шаг для машины разработчика: sixel в conhost 22000 отсутствует (F13),
картинку там рисуем только своим окном — как PictureView в Far, но без опоры
на доброту хоста (F12).

Почему: F6 (затирание) и F7/F8 (сцепка очередей и клин) — оба следствия
child-отношения с окном чужого процесса. Окно без parent и owner не имеет
ни того, ни другого.

Спецификация нового `overlay_windows.go` (состояние `overlay_state.go` и
геометрия `geometry.go` остаются; `Place/Draw/Hide/SetBounds/Visible/
ClientSize/Close/Stats` — тот же API для `image_console_overlay.go`):
1. **Создание** на pump-потоке: `CreateWindowExW(WS_EX_LAYERED|WS_EX_TRANSPARENT|
   WS_EX_TOOLWINDOW|WS_EX_NOACTIVATE, class, nil, WS_POPUP, 0,0,0,0,
   parent=0, menu=0, inst, 0)`. Константы: `WS_POPUP=0x80000000`,
   `WS_EX_LAYERED=0x80000`, `WS_EX_TRANSPARENT=0x20`, `WS_EX_TOOLWINDOW=0x80`,
   `WS_EX_NOACTIVATE=0x08000000`. HWND консоли хранить только как «цель
   слежения» (`target`), никогда не передавать в parent/owner.
   `WS_EX_TRANSPARENT` заменяет `HTTRANSPARENT` (мышь идёт в консоль);
   `WM_NCHITTEST`/`WM_ERASEBKGND`/`WM_PAINT` больше не нужны — layered-окно
   с `UpdateLayeredWindow` не получает WM_PAINT.
2. **Показ кадра** (`apply`, pump-поток): из RGBA-буфера кадра сделать
   32-bpp DIB (`CreateDIBSection`, `biHeight = -h` — сверху вниз,
   `BI_RGB`), переложить в **premultiplied BGRA**
   (`b*a/255, g*a/255, r*a/255, a`), выбрать в `CreateCompatibleDC(0)`,
   затем `UpdateLayeredWindow(hwnd, 0, &POINT{screenX,screenY}, &SIZE{w,h},
   hdcMem, &POINT{0,0}, 0, &BLENDFUNCTION{AC_SRC_OVER=0, 0, 255, AC_SRC_ALPHA=1},
   ULW_ALPHA=2)`. Позиция, размер и пиксели — один вызов, поэтому правило
   «двигать только в том пробуждении, где рисуем» выполняется само собой,
   а «чёрный прямоугольник до первого paint» невозможен. После первого
   успешного `UpdateLayeredWindow` — `ShowWindow(hwnd, SW_SHOWNOACTIVATE=4)`.
   Освободить DC/битмап после вызова. Экранные координаты кадра:
   `GetClientRect(target)` + `ClientToScreen(target, &POINT{0,0})`
   (оба не шлют сообщений).
3. **Регион/`SetBounds`** больше не нужен: промежутки между миниатюрами —
   просто alpha=0 в буфере (`buf` в `RenderExternal` уже нулевой там, где
   ничего не нарисовано). `SetBounds` оставить как no-op, возвращающий true,
   чтобы вызывающая сторона не менялась; `regionActive` можно удалить.
4. **Слежение за консолью** (pump-поток, `SetTimer(hwnd, 1, 33, 0)` →
   `WM_TIMER=0x0113`): на каждом тике, если окно должно быть показано:
   - `!IsWindow(target)` → `Close()` (консоль умерла);
   - `IsIconic(target) || !IsWindowVisible(target)` → `ShowWindow(SW_HIDE=0)`
     до следующей смены;
   - новый `ClientToScreen`/`GetClientRect` → если сдвинулось —
     `UpdateLayeredWindow(hwnd, 0, &pt, nil, 0, nil, 0, nil, 0)` (только позиция);
     если изменился размер клиентской области — просто ждать: f4 сам пришлёт
     новый кадр по изменению размера консоли (`FM_RESIZE`);
   - z-order: `prev := GetWindow(target, GW_HWNDPREV=3)`; если `prev != hwnd`:
     `after := prev`; если `prev == 0` или у `prev` есть `WS_EX_TOPMOST=8`
     (`GetWindowLongPtrW(prev, GWL_EXSTYLE=-20)`) → `after = HWND_TOP (0)`;
     `SetWindowPos(hwnd, after, 0,0,0,0, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE
     = 0x2|0x1|0x10)`. Так оверлей всегда ровно над консолью и под всем, что
     подняли выше неё. Если Q6 покажет проблемы — запасной вариант: показывать
     только пока `GetForegroundWindow() == target`, иначе прятать.
   - Улучшение (после того как таймер заработал): `SetWinEventHook(
     EVENT_SYSTEM_FOREGROUND=0x0003 … EVENT_OBJECT_LOCATIONCHANGE=0x800B,
     0, callback, pid консоли (`GetWindowThreadProcessId`), 0,
     WINEVENT_OUTOFCONTEXT=0|WINEVENT_SKIPOWNPROCESS=2)` на pump-потоке —
     тот же код пересчёта, но без задержки в 33 мс при перетаскивании окна.
     Хук доставляется через message loop потока, установившего его, ничего
     в conhost не внедряет. Снять `UnhookWinEvent` в `Close`.
5. **Инвариант «никто не ждёт pump-поток»** остаётся, но теперь его нарушить
   сложнее: у окна нет чужого parent/owner, а все вызовы к окну консоли —
   только читающие (`GetClientRect`, `ClientToScreen`, `IsIconic`,
   `IsWindowVisible`, `GetWindow`, `GetWindowLongPtrW`, `GetForegroundWindow`).
   Запрет на `SendMessage`/`SetWindowPos`/`ShowWindow` с чужим HWND —
   записать в шапку файла и в `WINCON.md`.
6. `wincon.New()` больше не может зависнуть на `CreateWindowExW` (нет сцепки
   очередей); таймаут 5 с оставить как страховку.
7. Тесты: премультипликация и упаковка BGRA — чистая функция
   `premultiplyBGRA(dst, src []byte, w, h, stride)` в файле без тега +
   тест (прозрачный, непрозрачный, полупрозрачный пиксель); решение
   «что делать на тике» — чистая функция `trackStep(state, observed) ops`
   с тестами (минимизирована / сдвинулась / умерла / prev==hwnd / prev topmost).
8. `WINCON.md` §1–2 переписать: §1 — как отличаем (класс окна + DA1), §2 —
   почему не child и не owned (F6, F7 со ссылками на Raymond Chen).

### Шаг 3a. Размер клетки под ConPTY

Там, где считается `IMAGE_GEOM`, нельзя брать клетку из
`GetCurrentConsoleFontEx`: под ConPTY её ширина равна нулю (F17). Порядок
источников: `CSI 16 t` → если ответа нет, размер в пикселях из `CSI 14 t`,
делённый на размер в клетках → и только для настоящего `ConsoleWindowClass` —
Win32 Console API. Тест на нулевую ширину обязателен: любое деление на неё
должно давать понятный отказ, а не панику.

## 4. Памятка пользователю: как собрать информацию по картинкам в консольном f4

Если жалоба именно «картинка пропадает/мелькает» — начинать надо с
`tools/f4imgprobe` (README на русском лежит рядом с ним): он задаёт восемь
вопросов и отвечает, какое именно событие стирает картинку на этой машине.
Для полного диагностического прогона по ConPTY и режимам reflow используйте
`tools/conptyprobe` (инструкция в его `README.md`). Версия 6 сама запускает forced conhost, явный Windows
Terminal и сценарий default-terminal handoff, а также сама перебирает режимы
`F4_WIN_REFLOW` у лежащего рядом `f4.exe`; вручную менять переменные между
прогонами не требуется. Следующие пункты нужны только для отдельного визуального
воспроизведения проблемы, которое автоматический ConPTY-прогон не заменяет.

1. Скажите, **где** запущен f4 (это три разных механизма):
   - классическое окно консоли (заголовок `cmd.exe`/`f4.exe`, нет вкладок);
   - Windows Terminal, запущенный командой `wt.exe f4.exe` или из его вкладки;
   - Windows Terminal, но f4 запущен ярлыком прямо на `f4.exe` (Win11 с WT
     «терминалом по умолчанию») — так тоже бывает, и это отдельный случай.
   Проверка: внутри f4 нажмите Ctrl+O и выполните `echo %WT_SESSION%`.
   Пусто — переменной нет, напишите это.
2. Версии: `ver` (сборка Windows), версия WT (Settings → About), сборка f4
   (Help → About или строка `F4 STARTUP` в логе).
3. Запуск с логом:
   ```
   set VTUI_DEBUG=1
   f4.exe
   ```
   откройте по F3 файл, на котором воспроизводится, подождите 10–15 с, выйдите
   (или снимите процесс). Приложите `debug.log` целиком и размер файла
   (пиксели и байты).
4. Если зависло: в Диспетчере задач посмотрите, **какой процесс** ест CPU —
   `f4.exe`, `conhost.exe`, `OpenConsole.exe` или `WindowsTerminal.exe`.
   Если умеете — Process Explorer → f4.exe → Properties → Threads → стек
   самого «горячего» потока, то же для `conhost.exe`.
5. Контрольный прогон: в `config.ini`, секция `[Images]`, строка `Overlay=0`
   (старое имя `X11Overlay=0` тоже действует). Сообщите, изменилось ли
   поведение (ожидается «[ Image graphics not supported ]» в конхосте Win10).
6. Скриншот всей области экрана, а не только окна: видно, где именно
   появляется/пропадает картинка.
