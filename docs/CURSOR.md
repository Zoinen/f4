# Курсор: пропадает каретка в диалогах и редакторе (issue #518)

Документ фиксирует результаты разбора issue #518 («Курсор», nz256, 18.08).
Все находки ниже воспроизведены на стенде; для каждой указано, чем именно
она подтверждена. Патчей по итогам разбора пока не подано — см. §8
«Развилка», её нужно закрыть решением мейнтейнера.

## 0. Краткая сводка

1. **Основная причина в диалогах** — граничный уход фокуса из `Edit` по
   Left/Right (`vtui/edit.go`). Каретка не «гаснет» — фокус уезжает на
   соседний контрол, у которого каретки нет. §2
2. **Причина в редакторе** — `EditorView.DisplayObject` рисует каретку без
   проверки фокуса, поэтому при модальном диалоге сверху каретка появляется
   в тексте **под** диалогом. §3
3. **Фикс, добавленный 20.08 (keepalive), нерабочий**: его предпосылка о
   поведении VTE неверна, и сам он не сбрасывает то, что должен. §4
4. Попутно найдены два самостоятельных дефекта в `vtui`: `SetCursorPos`
   молча гасит курсор (§5) и `AnsiRenderer.write()` игнорирует короткую
   запись (§6).

Версии, на которых всё воспроизведено: `f4` @ `c65a81d`, `vtui` `v0.1.253`
(= `5cf9b8e`), Go 1.26.0, linux/amd64, `TERM=xterm-256color`, терминал
100x30, ANSI-бэкенд (без `--gui`).

## 1. Стенд

Бинарь гоняется в настоящем pty, вывод параллельно скармливается эмулятору
терминала (`pyte`) и разбирается на escape-последовательности. Это даёт
одновременно две картины: что видит пользователь (экран, атрибуты ячеек,
позиция и видимость курсора) и что именно f4 послал в терминал
(`ESC[?25h` / `ESC[?25l`, CUP, DECSCUSR).

Оракул для поиска бага: кадр закончился со скрытым курсором **и** ввод
печатного символа после этого продолжает попадать в поле ввода. Такое
сочетание означает «поле в фокусе, а каретки нет» — это баг. Просто
скрытый курсор багом не является: при фокусе на кнопке каретки быть и не
должно, это штатное поведение Far.

Все сценарии ниже детерминированы и воспроизводятся с первого раза.

## 2. Находка 1: граничный уход фокуса из `Edit` (диалоги)

### Репро

`F7` (Create Folder) → набрать `abc` → нажать **Right** один раз.
Каретка немедленно пропадает, дальнейший ввод в поле не попадает.
Симметрично: **Left** в позиции 0.

Подтверждено ровно тем же способом в:

- `F7` — Create Folder;
- `F6` — Rename or move;
- `Shift+F4` — create new file;
- `F7` внутри редактора — диалог Search (поле «Search for:»).

То есть весь список из тикета, кроме собственно редактора (см. §3).

### Причина

`vtui/edit.go`, `Edit.ProcessKey`:

```go
case vtinput.VK_LEFT:
    if isAtStart && !shift && !ctrl {
        return false // Escape focus to previous
    }
...
case vtinput.VK_RIGHT:
    if isAtEnd && !shift && !ctrl {
        ...
        return false // Escape focus to next
    }
```

На границе поле возвращает `false`, событие всплывает в
`Group`/`BaseWindow.ProcessKey`, и фокус переходит на следующий по порядку
`AddItem` контрол. В диалоге mkdir (`cmd/f4/actions.go`, `actionMkDir`)
порядок такой: `lblPrompt`, `editName`, `comboMode`, `btnOk`, `btnCancel`,
то есть следующий — комбобокс режима операции (`Queue ↓`, `DropdownOnly`),
у которого каретки нет по определению.

### Почему это выглядит как «пропал курсор»

Подсветка фокуса у комбобокса меняется — проверено по атрибутам ячеек,
фон строки `Queue` переключается с `c4b8a8` на `e6b450`. Но пользователь,
набирающий имя папки, смотрит на каретку, а не на фон соседнего элемента.
Субъективно: «я печатал, нажал стрелку — курсор исчез и текст больше не
вводится».

### Статус: не баг реализации, а следствие гайдлайна

Поведение **намеренное** и задокументировано в `vtui/UX_GUIDELINES.md`,
Tier 2, «Boundary Behavior»:

> Arrow keys transfer focus to a neighboring component only when the cursor
> is at the absolute boundary of the current component's data set.

При этом оно расходится с заявленной целью f4 воспроизводить UX Far: в
диалогах Far Manager стрелки Left/Right внутри строки ввода фокус не
переносят, это делают Tab/Shift+Tab и Up/Down. Up/Down в наших диалогах
работают как в Far и претензий не вызывают.

Отсюда развилка §8.

## 3. Находка 2: `EditorView` рисует каретку без проверки фокуса

### Репро

Открыть редактор (`F4`), поставить каретку, например, на 2-ю строку, 3-ю
колонку. Нажать `F7` (Search), набрать `one`, нажать **Right**. Фокус по
механизму §2 уходит с поля на чекбокс, и каретка **появляется в тексте под
диалогом** — ровно в позиции каретки редактора (проверено: экранные
координаты каретки совпадают с позицией до открытия диалога). Tab по
контролам диалога её оттуда не убирает.

### Причина

Кадр рисуется снизу вверх, и фрейм под верхним никак не узнаёт, что над
ним что-то появилось: он продолжает выставлять экранный курсор из
собственного состояния. `EditorView.DisplayObject` делает это на своей
каретке, `PanelsFrame` — на командной строке. Обычно верхний фрейм
перекрывает установку своим сфокусированным полем ввода, и ничего не
видно. Но если в верхнем фрейме в фокусе контрол без собственной каретки
(чекбокс, кнопка, `DropdownOnly` комбобокс), перекрывать нечем — и на
экране остаётся каретка нижнего фрейма.

Проверка `ev.IsFocused()` в `EditorView` эту задачу **не решает**: это
флаг самого объекта, и у фрейма редактора он остаётся `true`, когда сверху
открыт модальный диалог. Проверено на стенде — правка оказалась пустышкой
и была отброшена.

Чинится в общем рендер-цикле `vtui/framemanager.go`: состояние курсора,
оставленное любым фреймом кроме самого верхнего, отбрасывается сразу после
его отрисовки. Это лечит весь класс, а не только редактор.

Заметим, что для пользователя это выглядит не как «каретки нет», а как
«каретка не там, где я печатаю» — что тоже описывается словами «пропадает
курсор», и объясняет пункт «и самое главное в редакторе текста».

## 4. Находка 3: keepalive из `53495b5` не работает

20.08 в `vtui` (внутри коммита `53495b5`, заголовок которого посвящён
`win32_console`) добавлены `AnsiRenderer.TouchCursorForBlinkKeepalive()`,
`ScreenBuf.TouchCursorKeepalive()` и горутина в `framemanager.Run`, раз в 5
секунд делающая `PostTask` → `TouchCursorKeepalive()` + `Redraw()`.
Заявленная цель — не дать GTK/VTE-терминалам заморозить собственное мигание
курсора по `gtk-cursor-blink-timeout`.

Обе половины этой конструкции не выдерживают проверки по исходникам VTE
(`src/vte.cc`).

### 4.1. Предпосылка неверна: VTE замирает с **видимым** курсором

```c
bool Terminal::cursor_blink_timer_callback()
{
        m_cursor_blink_state = !m_cursor_blink_state;
        m_cursor_blink_time_ms += m_cursor_blink_cycle_ms;
        invalidate_cursor_once(true);
        /* only disable the blink if the cursor is currently shown.
         * else, wait until next time. */
        if (m_cursor_blink_time_ms >= m_cursor_blink_timeout_ms &&
            m_cursor_blink_state) {
                return false;
        }
        ...
}
```

Таймер останавливается только при `m_cursor_blink_state == true`, а в
`paint_cursor()` условие непрорисовки — `if (focus && !blink) return;`,
то есть `true` = курсор нарисован. Значит замирание оставляет курсор
**видимым** и причиной его пропажи быть не может.

Условие сверено в версиях 0.36.5, 0.44.2, 0.52.2, 0.58.3, 0.64.2, 0.70.6,
0.76.0, 0.78.0 и master — оно везде одинаковое. Гипотезу «старый VTE
замирает в фазе OFF» проверка не подтверждает.

### 4.2. Даже если бы подтвердилась — keepalive ничего не сбрасывает

`m_cursor_blink_time_ms` обнуляется ровно в одном месте:

```c
void Terminal::add_cursor_timeout()
{
        if (m_cursor_blink_timer)
                return; /* already added */
        m_cursor_blink_time_ms = 0;
        ...
}
```

Пока таймер жив — ранний выход, обнуления нет. Единственный путь сбросить
таймаут — довести `check_cursor_blink()` до `remove_cursor_timeout()` и
затем обратно до `add_cursor_timeout()`, то есть провести переход
`m_has_focus && m_cursor_blinks && DEC_TEXT_CURSOR()` из false в true.

Вдобавок `process_incoming()` вызывает `check_cursor_blink()` только если
курсор сдвинулся либо сменилась его видимость/стиль. Повторная отправка
идентичных CUP + `ESC[?25h` + DECSCUSR не меняет ни того, ни другого.

### 4.3. Цена

Каждые 5 секунд бесконечно: `PostTask` + полный `Redraw()` + флаш кадра на
каждой ANSI-сессии. Это ровно то «лишнее дёрганье» рендера в простое, ради
устранения которого 18.08 (`c74f04a`) idle-хартбит был исключён для
нативных бэкендов, см. `docs/WINE.md` §3.1.

Рекомендация: keepalive снять целиком, вместе с маркерным интерфейсом
`ansiCursorKeepaliveRenderer`.

## 5. Находка 4: `SetCursorPos` молча гасит курсор

`vtui/screenbuf.go`:

```go
func (s *ScreenBuf) SetCursorPos(x, y int) {
    ...
    if s.width <= 0 || s.height <= 0 || x < 0 || x >= s.width || y < 0 || y >= s.height {
        s.cursorVisible = false
        return
    }
    ...
}
```

Два отдельных дефекта:

- сеттер **позиции** меняет **видимость** — побочный эффект, о котором
  вызывающий код не знает;
- при этом не выставляется `cursorDirty`, то есть изменение состояния не
  помечается грязным.

Усугубляется тем, что порядок вызовов в кодовой базе разный:

| место | порядок | что победит при выходе за границы |
|---|---|---|
| `vtui/edit.go:151` | `SetCursorVisible(true)` → `SetCursorPos()` | гашение |
| `cmd/f4/editor_view.go:1612` | `SetCursorPos()` → `SetCursorVisible(true)` | показ |
| `vtui/multilineedit.go:213` | `SetCursorPos()` → `SetCursorVisible(true)` | показ |

Итог: одно и то же граничное условие в разных виджетах даёт разный
результат. Воспроизвести пропажу каретки через этот путь на стенде не
удалось (см. §7), но код неверен независимо от этого.

## 6. Находка 5: `AnsiRenderer.write()` теряет данные при короткой записи

`vtui/screenbuf.go`:

```go
for len(s) > 0 {
    n := len(s)
    if n > writeChunk {
        n = writeChunk
    }
    io.WriteString(w, s[:n])
    s = s[n:]
}
```

И ошибка, и фактическое число записанных байт игнорируются: срез
сдвигается на запрошенную длину. Короткая запись молча теряет хвост чанка.

Для курсора это прямой путь к симптому из тикета: каждый непустой кадр
открывается `ESC[?2026h ESC[?25l`, а `ESC[?25h` приходит в самом конце.
Обрезанный кадр оставляет курсор скрытым до ближайшей смены его состояния.

## 7. Что проверено и исключено

Чтобы следующая сессия не ходила по кругу:

- **`?25l` без парного `?25h` в обычных кадрах** — не подтверждается.
  `Render()` вместе с `ESC[?25l` выставляет `termCursorInvalid = true`, и
  `PrepareFlush()` гарантированно дописывает позицию и видимость. На
  стенде каждый `HIDE` идёт в паре со `SHOW` в том же кадре.
- **Небалансный synchronized update (mode 2026)** — не подтверждается.
  `?2026h` пишет только `Render()`, `?2026l` дописывается при непустом
  `frameOut`. Обратный случай (лишний `?2026l` без открывающего) возможен,
  но безвреден.
- **Выход каретки за правый край экрана в командной строке** — не
  воспроизводится: `Edit` скроллит текст, каретка упирается в последнюю
  колонку и остаётся видимой (проверено набором 120 символов при ширине
  100).
- **Пропажа каретки в редакторе от обычных клавиш редактирования** — не
  воспроизводится: 4 прогона фуза по 80 шагов (стрелки, Home/End, PgUp/
  PgDn, Ctrl+стрелки, Shift+стрелки, Del/BS, Ins, Tab, Ctrl+B/K/Y/Z/U/F)
  не дали ни одного кадра со скрытой кареткой.
- **Idle сам по себе** — в простое f4 не пишет в терминал вообще ничего,
  так что «пропажа в простое» может быть только поведением терминала; §4
  показывает, что у VTE такого поведения нет.

Мелочь на будущее: поле `ScreenBuf.cursorDirty` фактически вестигиально —
оно выставляется и сбрасывается, но нигде, кроме тестов, не читается.

## 8. Решение по §2 и состояние работ

Граничный уход фокуса из §2 признан **штатным поведением** и остаётся как
есть: он удобнее на практике, соответствует Tier 2 в
`vtui/UX_GUIDELINES.md` и правке не подлежит. Расхождение с Far здесь
сознательное.

Соответственно поданы патчи только по остальным находкам:

| находка | где | статус |
|---|---|---|
| §3 каретка под модальным диалогом | `vtui/framemanager.go` | патч + тест, проверено на стенде |
| §5 `SetCursorPos` гасит курсор | `vtui/screenbuf.go` | патч + тест |
| §6 короткая запись | `vtui/screenbuf.go` | патч + тест |
| §4 нерабочий keepalive | `vtui/framemanager.go`, `screenbuf.go` | удалён |

Все три коммита — в `vtui`, набор тестов зелёный, f4 против пропатченной
`vtui` собирается, сценарии стенда (каретка в панелях, в диалоге mkdir, в
редакторе, в диалоге поиска и после его закрытия) регрессий не дают.
После вливания в `vtui` нужен бамп версии в `go.mod` f4.
