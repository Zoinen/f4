# Инструкция для модели, работающей на Windows

Ты работаешь на настоящей Windows и можешь запускать нативный ConPTY. Это
твоё главное преимущество: предыдущие сессии этого не могли и потому
догадывались о поведении консоли. Догадки стоили проекту удаления 25 тысяч
строк кода. Не повторяй.

## Прежде чем что-либо делать

1. **Обновись из репозитория.** `git fetch && git checkout main && git pull`.
   Работа идёт быстро и параллельно; патч против устаревшего дерева не
   применится, а выводы про устаревший код будут неверными.
2. Прочитай в таком порядке:
   - `docs/CONPTY_GATE_REQUIREMENTS.md` — **закрытый список требований**.
     Первый раздел — строжайший запрет на эвристики, второй — запрет на
     привязку к f4. Новых требований по ходу дела не будет;
   - `docs/PINNED_HOST_FACTS.md` — что установлено **по исходнику** пиннутого
     хоста, со ссылками на файл и строку. Вопрос о поведении хоста — сначала
     сюда, потом в исходник, и только потом в прогон;
   - `docs/PINNED_CONSOLE.md` — какой хост, какой коммит, единственный
     сохранённый факт наблюдения, разбор прошлых провалов;
   - `docs/CONPTY_NATIVE_AUDIT.md` — что доказано, что нет, что открыто;
   - `docs/CONPTY_NATIVE_TEST.md` — как устроен тест технически;
   - `docs/CONPTY_FUTURE_IDEAS.md` — соображения на перспективу
     (производительность, кластеры графем, что хост пробрасывает насквозь).
     Не план работ: ничего оттуда не делается без отдельного решения.
3. Проверь, не устарел ли аудит: он датирован и привязан к коммиту. Появились
   новые коммиты — сначала пересмотри выводы, потом работай.

## Что именно доказывается

Гейт — **самостоятельный инструмент** `tools/conptyreconcile` с собственным
Go-модулем. Он доказывает синтетически, что режим из ТЗ достижим за счёт
свойства пиннутого OpenConsole отдавать длинные строки целиком:

1. **побайтово точная история** — всё, что напечатал ребёнок между маркерами,
   восстанавливается ровно один раз, в том же порядке, теми же байтами;
2. **динамический reflow** — при смене ширины логические строки
   перевыкладываются без потерь;
3. **устойчивость в экстремальных условиях** — включая изменение размера окна
   прямо во время выдачи `dir`.

Результат — референс по использованию API, пригодный для любого терминала, а
не только для f4.

## Три жёстких запрета

**Никаких эвристик.** Восстанавливать логические строки из рядов сетки
запрещено: ряд не несёт границы строки, поэтому её приходится угадывать — по
флагу переноса, по заполненности ряда, по хвостовым пробелам, по «значимой
ширине». Пиннутый хост отдаёт длинную строку одним куском без CRLF в точке
переноса, то есть граница задана явным переводом строки, и угадывать нечего.
Строка хранится целиком с момента получения; нарезка по ширине — только при
отрисовке. Реализация, которая так не умела, удалена целиком вместе со своими
счётчиками потерь; восстанавливать её нельзя. Кажется, что без догадки не
обойтись — значит, данные берутся не оттуда: остановись и напиши об этом.

**Никакой привязки к f4.** Проверка идёт по полному пути внутри инструмента:
живая сессия пиннутого хоста → накопление целых логических строк → история,
экран, курсор. Прогон потока через `PanelsFrame`/`AnsiParser`/`TerminalView`
гейтом не является ни в каком виде, включая opt-in диагностику. Гейт не импортирует f4, не собирает f4, не
проверяет f4 и не упоминает его — ни в маркерах, ни в путях кэша, ни в
комментариях «для будущего адаптера f4». Код гейта не живёт в `cmd/f4`; файлы
`cmd/f4/native_openconsole_*` удалены и возвращать их туда не нужно.
Интеграция в f4 — отдельная работа после того, как гейт пройден.

**Не трогать текущее поведение f4.** Под Windows там нет reflow и есть точная
история — это корректный fallback и поведение по умолчанию, когда пиннутый
OpenConsole не найден. Задача гейта — не чинить нынешний f4, а доказать
осуществимость режима из ТЗ.

## Правила работы

Не подменяй хост: только `OpenConsole.exe` из `docs/PINNED_CONSOLE.md`, с
проверкой личности живого процесса. Недоступен — hard failure, не skip.

Не удаляй измеренные факты и записи об ошибках. Удалять можно описание
отвергнутого подхода. Если документ устарел целиком — перенеси из него факты и
разбор ошибок в новый, потом удаляй.

Не считай по памяти: любое число в отчёте получено командой, которую можно
перезапустить.

Не отчитывайся о готовности при половине сделанного. Сделано шесть пунктов из
десяти — так и напиши, назвав оставшиеся четыре.

## Порядок работ

Порядок — рекомендация, составленная без доступа к Windows. **Ты видишь живую
систему, автор рекомендации — нет.** Меняй порядок, если прогон показал, что
он неверен, и объясняй почему. Право решать за тобой; требование одно —
решение обосновано прогоном, а не удобством.

1. **Хранение целых логических строк.** Внутри инструмента: поток пиннутого
   хоста → логические строки, границы берутся из явных переводов строки.
   Никакой сборки из рядов. Это фундамент, без него остальное бессмысленно.
2. **Точная история (раздел A).** Сверка с `expected_input` целиком и
   побайтово: каждая строка ровно один раз, порядок, маркеры по одному,
   никаких лишних переводов строки. Строки точной длины `N-1/N/N+1/2N+1`,
   одинаковые повторяющиеся строки, повторяющиеся символы, пробельные и
   пустые строки, Unicode вплоть до составных символов и Bidi, управляющие
   последовательности, альтернативный экран.
3. **Динамический reflow (раздел B).** Перевыкладка целых строк при смене
   ширины; после каждого изменения размера свойство A проверяется заново
   целиком, плюс экран, история, позиция курсора. Последовательности размеров
   из требований, включая возврат к исходному.
4. **Экстремальные условия (раздел C).** Resize во время активного
   рекурсивного `dir`, серия быстрых resize, произвольные границы чтения с
   разрывом UTF-8 и escape-последовательностей, прокрутка и вытеснение,
   жизненный цикл.
5. **Реальные команды (A4)** и **фаззинг с 300 сидами (D3).**

### Размер шага: группируй независимое

Требование «не отчитываться о готовности при половине сделанного» — про
**честность отчёта**, а не про размер шага. Оно не означает «коммит после
каждого измерения».

Если несколько пунктов не зависят друг от друга — ни один не меняет условий
другого, ни один не может отменить остальные, — собирай их в **один заход**:
один payload на несколько классов строк, одна серия прогонов, один коммит,
один отчёт. Это дешевле и по времени, и по вниманию читателя.

Отдельный коммит нужен, когда результат **меняет план**: опровергает
записанный факт, вскрывает новый механизм, требует правки требований или
делает следующий шаг бессмысленным. Такое надо фиксировать сразу и отдельно,
чтобы оно не потерялось в группе.

Проверка простая: если результат прогона не заставит переписать ни одного
пункта в `PINNED_HOST_FACTS.md` и не изменит порядок работ — его место в
группе, а не в отдельном коммите.

## Как отчитываться

После каждого шага обнови `docs/CONPTY_NATIVE_AUDIT.md`: что стало доказано,
что осталось, какие расхождения закрыты и чем. Устаревшие утверждения удаляй,
факты и записи об ошибках переноси.

В отчёте: что сделано, что осталось, какие числа получены какой командой.
Не удалось — скажи, что именно мешает. Названный вслух blocker полезнее
зелёного отчёта, который через день окажется ложным.
