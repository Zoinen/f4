# Нативный тест ConPTY на Windows

## Цель

Проверять алгоритм терминала f4 на настоящем Windows ConPTY с настоящим
`OpenConsole.exe` нужной версии. Тест не должен воспроизводить поведение
консоли в Go, копировать исходники Microsoft или сравнивать две самодельные
модели. Единственный источник наблюдаемого поведения в этом gate — запущенный
нативный host.

Это Windows-only интеграционный тест. Обычные тесты f4 и их test doubles
остаются отдельным, быстрым уровнем проверки; они не заменяют этот прогон.

Первый handoff-артефакт для реализации — standalone probe в
[`docs/CONPTY_NATIVE_PROBE.md`](CONPTY_NATIVE_PROBE.md). Он уже запускает
пинованный host через тот же native ConDrv/`--headless` plumbing и сохраняет
сырые наблюдения; полноценный gate ниже станет зелёным только после подачи
этого потока через реальный f4 terminal session и проверки screen/history.

Закрытый список требований, по которому гейт считается пройденным:
[CONPTY_GATE_REQUIREMENTS.md](CONPTY_GATE_REQUIREMENTS.md). Этот документ
описывает, как тест устроен; требования — что он обязан доказать.

Текущее состояние работ и открытые расхождения:
[CONPTY_NATIVE_AUDIT.md](CONPTY_NATIVE_AUDIT.md). Пиновка хоста, единственный
сохранённый факт наблюдения и разбор прошлых провалов:
[PINNED_CONSOLE.md](PINNED_CONSOLE.md). Инструкция исполнителю:
[CONPTY_NATIVE_AGENT.md](CONPTY_NATIVE_AGENT.md).

## Целевой host

Для воспроизводимости используется один зафиксированный бинарник из
официального релиза Windows Terminal:

| Поле | Значение |
|---|---|
| Бинарник | `OpenConsole.exe`, x64 |
| FileVersion/ProductVersion | `1.12.220408003-release1.12` |
| Пакет | `CascadiaPackage_1.12.10983.0_x64.msix` |
| SHA-256 `OpenConsole.exe` | `14e0857b37f6c5e5e90bab786a4db8fceb4166afe75e617519d942656976481e` |
| Официальный asset | [`Microsoft.WindowsTerminal_Win11_1.12.10983.0_8wekyb3d8bbwe.msixbundle`](https://github.com/microsoft/terminal/releases/download/v1.12.10982.0/Microsoft.WindowsTerminal_Win11_1.12.10983.0_8wekyb3d8bbwe.msixbundle) |

Системный `conhost.exe`, установленный Windows Terminal, `wt.exe`, Wine и
другая версия `OpenConsole.exe` не являются заменами. Если host нельзя
скачать, распаковать, проверить или запустить, явно запущенный gate должен
завершиться ошибкой, а не превратиться в зелёный skip.

## Автоматическая подготовка на Windows

Тест должен сам выполнить следующие действия перед первым сценарием:

1. Вычислить URL и ожидаемые значения из одной тестовой манифестной записи.
   Не искать установленный Windows Terminal и не брать бинарник из `PATH`.
2. Скачать asset по HTTPS в пользовательский кэш вне рабочего дерева, например
   `%LOCALAPPDATA%\f4\native-conpty\1.12.10983.0\`. Повторный запуск
   использует кэш только после проверки SHA-256; частичный или повреждённый
   файл скачивается заново. Запись кэша должна быть защищена от двух
   одновременных тестов.
3. Распаковать `.msixbundle` как ZIP во временный каталог, найти внутри
   `CascadiaPackage_1.12.10983.0_x64.msix`, затем распаковать и его. Запускать
   нужно полный каталог x64-пакета с соседними DLL, а не файл, скопированный
   в случайный каталог. Устанавливать AppX/MSIX в систему не требуется.
4. Найти ровно один `OpenConsole.exe`, прочитать его version resource через
   Windows API и посчитать SHA-256. Несовпадение имени, архитектуры, версии или
   хэша — hard failure с путём и фактическими значениями.
5. Удалить временные каталоги после успешного прогона только если не включён
   режим сохранения артефактов. Кэш проверенного пакета оставлять можно.

Загрузка должна быть частью запуска теста: на чистой Windows-машине достаточно
одной команды `go test`, без ручной установки Windows Terminal и без заранее
положенного рядом `OpenConsole.exe`.

## Архитектура теста

Добавить Windows-only host-session adapter и интеграционный тест рядом с
потребителем потока внутри самого инструмента; в `cmd/f4` код гейта не живёт.
Разделить ответственность так:

- adapter занимается только загрузкой/проверкой файла, созданием нативной
  ConPTY-сессии, запуском выбранного `OpenConsole.exe`, подключением дочернего
  процесса, чтением/записью pipe и ResizePseudoConsole/нативным resize;
- parser, `TerminalView`, scrollback, reflow и прочие алгоритмы берутся из
  текущего f4-кода;
- adapter не содержит таблиц ширины, screen buffer, VT renderer, правил wrap,
  frame splitter или «исправлений» поведения host;
- `OpenConsole.exe` запускается по абсолютному проверенному пути. Вызов
  обычного `NewPTY`, который отдаёт выбор host операционной системе, недостаточен
  для этого gate: тест должен доказать, какой процесс был запущен.

Если для запуска standalone `OpenConsole.exe` нужна Windows-specific связка
ConDrv/handle или режим `--headless`, её следует изолировать в маленьком
Windows adapter и тестировать как plumbing. Это не разрешает переносить в f4
код экрана, parser, renderer или иные семантики OpenConsole.

Каждая сессия должна иметь новый временный каталог, уникальный набор маркеров и
ограниченное время жизни. Закрытие выполняется в порядке, гарантирующем, что
дочерний процесс, host и pipes не оставят зависший тест.

## Что считать правильным результатом f4

Пробник обязан проходить через тот же путь, которым пользуется настоящий f4:
`PanelsFrame`/его terminal session, `AnsiParser`, `TerminalView`, scrollback и
UI-task delivery. Снимок только сырых bytes или прямой вызов parser в обход
реального session path недостаточен. Если тестовый harness временно вызывает
внутренние части по отдельности, это должны быть дополнительные диагностические
проверки, а не зелёный результат native gate.

Каноническая проверка текста — единый лог f4 в логическом порядке: уже
вытесненная история (`PieceTable`), `GridHistory` и текущий viewport. Для этого
нужно использовать существующий путь `TerminalView.GetAllLogBytes()` либо
вынести его в явно тестируемый API, но не собирать второй «ожидаемый экран» в
adapter. Длинная логическая строка должна оставаться одной точной строкой в
этом общем логе, даже если она пересекла viewport/history seam, была разбита
переносом, а затем окно несколько раз сузили и расширили. Проверять нужно
отсутствие потерь, дублей, перестановок, лишних переводов строк и обрезанных
хвостов; отдельно проверять видимый экран, прокрутку в историю и возвращение в
текущий viewport.

«1:1» здесь означает точное соответствие логическому payload, который child
вывел между маркерами, в общем логе f4 и в проверяемых срезах screen/history.
Сырые bytes ConPTY не обязаны быть byte-for-byte равны заранее придуманному
логу: native host может выбрать другой repaint, CR/LF или последовательность
перерисовки. Сырой поток всё равно сохраняется для диагностики, а ожидаемый
payload строится независимо от реализации parser и сравнивается с результатом
f4.

Изменение ширины должно проверять динамический reflow, а не только сохранение
последних строк: после каждого resize заново сверяются экран, история, cursor
position и единый лог. Если текущий Windows-путь пока отключает горизонтальный
reflow, это фиксируется как незакрытый production gap следующего шага; тест не
должен молча заменить его проверкой «panic не было».

## Сценарии

Сценарий запускает реальный child process (минимум `cmd.exe /d /q /c`) и
подаёт его поток в существующий f4 parser/terminal view. В поток входят
маркеры начала и конца каждой фазы, Unicode, строки около границы ширины,
управляющие последовательности, очистка, cursor movement и повторяющиеся
одинаковые строки. Обязательны:

- recursive `dir` с уникальными маркерами до и после команды;
- повторный `dir` с большими, но ограниченными fixture-каталогами, чтобы
  проверить backpressure и выдачу длиннее viewport; окружение должно очищать
  `DIRCMD`, а paging нужно явно отключать или обрабатывать по отдельному
  сценарию;
- строки из одного повторяющегося символа, чередующихся символов, пробелов,
  пустые строки, одинаковые строки, строки длиной `N-1`, `N`, `N+1`, `2N+1` и
  существенно длиннее viewport;
- ASCII, UTF-8, узкие и широкие Unicode-символы, combining marks, emoji и
  неоднозначные по ширине последовательности; кодировка, locale и способ
  вывода должны быть записаны в отчёт, а Unicode-fixture не должен случайно
  зависеть от системной code page;
- типичные ограниченные выдачи команд (`echo`, `type`, `findstr`, recursive
  `dir`, а при наличии PowerShell — `powershell -NoProfile -NonInteractive`),
  с маркерами начала/конца и проверкой exit code. Pager, подтверждение,
  интерактивный пароль и бесконечный progress не должны повесить gate;
- произвольные VT-последовательности: CR/LF, tabs, SGR, erase, абсолютное
  перемещение cursor, повторная запись строки, OSC title и, если это реальный
  путь f4, OSC 133 prompt/command markers;
- primary и alternate screen, переходы между ними, cursor position и resize в
  каждой фазе, если данный режим поддерживается текущим pipeline. Неподдержанный
  режим нельзя тихо пропустить: его нужно записать отдельным blocker-ом плана;
- точные ширины `1`, `N-1`, `N`, `N+1`, узкое и широкое окно, высоты `1`,
  `N-1`, `N`, `N+1`, повторное narrowing/widening и height-only resize;
- resize прямо во время активного вывода `dir` или другого длинного child
  output, включая серию быстрых resize и случай, когда один read chunk
  пересекает границу resize;
- произвольные границы чтения, включая разрыв UTF-8, CR/LF, CSI, OSC, OSC 133
  и несколько логических строк в одном chunk;
- прокрутка между history и viewport до/после resize, вытеснение в `PieceTable`,
  длинные строки на границе вытеснения и точное восстановление cursor;
- bounded timeout на каждую фазу, watchdog на всю сессию и сохранение первого
  несоответствия вместе с полным контекстом, а не только с итоговым boolean.

Проверяются свойства f4 и жизненный цикл сессии: каждый маркер появляется
ровно нужное число раз и в нужном порядке, вывод не теряется при resize,
различные разбиения одного потока дают один логический результат, а завершение
child не маскируется prompt-эхом. На каждой контрольной точке сравниваются
общий лог, видимая часть и history; нельзя проверять только финальный экран,
потому что он не обнаружит потерю уже прокрученного текста. Байт-в-байт
ожидаемый вывод host заранее не задаётся: VT-последовательности и repaint
являются фактическим результатом именно этой нативной версии.

## Фаззинг времени и реального f4

Каждый сценарий должен иметь детерминированный PRNG от seed. Он выбирает не
только данные, но и моменты небольших задержек и событий:

- перед/после записи child, возврата host read, передачи chunk в parser,
  постановки UI task, redraw, resize, marker и закрытия pipe;
- до, во время и сразу после выдачи длинной команды; обязательный случай —
  resize пока `dir` ещё пишет, а не только после его завершения;
- задержки нулевой длины, короткие случайные задержки и редкие более длинные
  задержки для выявления backpressure. Случайный `sleep` не является
  синхронизацией: фазы завершаются по marker/exit/semantic milestone, с
  watchdog и отменой.

Фаззинг не должен превращать корректный порядок событий в недетерминированный
ожидаемый результат. В отчёте фиксируются seed, выбранные задержки, порядок
read/resize/UI events и все timestamps; повтор того же seed воспроизводит ту же
последовательность. Там, где native host сам меняет repaint, проверяется
логический порядок markers/payload и состояние f4, а не случайная byte-level
форма repaint.

Гейт должен упражнять именно реальные точки риска f4:

- prompt ownership, command echo и завершение команды: не принять echo за
  payload, не продублировать f4-injected command, не считать prompt концом
  команды раньше времени, дождаться child exit и контрольного marker;
- отдельный жизненный цикл child/host/pipes: startup, первый prompt, ошибка
  запуска, EOF, broken pipe, cancellation, timeout и закрытие в каждом
  порядке. После seed не должно оставаться процессов, handles или goroutines;
- backpressure, частичные writes, пустые reads, EOF посреди escape sequence,
  неполные UTF-8/CSI/OSC и chunk с несколькими событиями;
- минимальный, нулевой/свёрнутый и очень широкий размер, недопустимый resize,
  изменение высоты без ширины, resize primary/alternate screen и redraw после
  возврата из alternate screen;
- mutex/async UI delivery и глобальное состояние f4: новый frame/session на
  каждый seed, `t.Cleanup`, отсутствие утечки задач и cross-seed contamination;
- окружение запуска: рабочий каталог, `DIRCMD`, `PAGER`, `GIT_PAGER`,
  `GIT_TERMINAL_PROMPT`, code page, locale, наличие/отсутствие `WT_SESSION`,
  Windows version, arch и командные строки всех процессов. PowerShell — с
  `-NoProfile -NonInteractive`, если он участвует в сценарии;
- ограничение памяти и размера артефактов: большой вывод должен создавать
  backpressure, но не бесконечный файл; truncation недопустима без явного
  failed assertion, а успешный результат обязан иметь END marker, exit code и
  полный лог до него.

Для каждой контрольной точки полезно хранить пару «ожидаемый логический
payload / фактический `GetAllLogBytes()`», а также отдельные screen/history
снимки. Это позволяет отличить ошибку host plumbing, parser, wrap/reflow,
scrollback, prompt ownership и UI race, не подменяя их одной общей ошибкой.

## 300 seed gate

После базовых сценариев запускается ровно 300 независимых seed. Это не Linux
тест и не тест самодельного mock. Каждый seed выполняется через новый процесс
нативного `OpenConsole.exe` и проверяет тот же f4 pipeline.

Seed управляет воспроизводимыми вариантами:

- содержимого и Unicode-последовательностей;
- размеров `N-1/N/N+1`, height и последовательности resize;
- границ чтения и interleaving вывода с resize;
- нулевых и небольших задержек в случайных точках записи, чтения, parser,
  UI-delivery, redraw, resize и lifecycle;
- набора команд и уникальных маркеров.

Каждый seed обязан прогнать полный native session и полный набор обязательных
assertions: host identity, command/marker order, unified f4 log, screen и
history snapshots, long-line exactness, resize/reflow timeline, EOF/exit и
отсутствие зависших процессов. Список из 300 seed и параметры каждого
сценария сохраняются в отчёте. Падение останавливает gate с ненулевым кодом,
но печатает сводку уже выполненных seed.
Отдельный повтор одного seed должен запускаться параметром вроде
`F4_NATIVE_CONPTY_SEED=...` и не скачивать заново уже проверенный пакет.

Нельзя засчитывать gate по отсутствию panic, по совпадению двух копий
алгоритма или по одному успешному startup. Нужны реальные команды, маркеры,
resize/interleaving, состояние f4, точный единый лог, полный набор артефактов и
все 300 успешных native sessions. Те же seed на Linux, mock host или
самодельной модели могут быть полезным быстрым уровнем, но не закрывают этот
gate.

## Диагностика и отладка

При ошибке сохраняются в отдельный каталог:

- seed и полное описание сценария;
- URL/имя asset, путь к извлечённому host, version resource и SHA-256;
- версия Windows и архитектура процесса;
- команда child и временные размеры;
- точная timeline resize и чтения;
- сырой байтовый вывод ConPTY;
- вход f4 parser и снимки состояния `TerminalView`: `PieceTable`,
  `GridHistory`, viewport, cursor, размеры, scroll offset и общий лог;
- ожидаемый логический payload каждой фазы, фактический `GetAllLogBytes()` и
  screen/history slices на каждой контрольной точке;
- первый mismatch, byte offset и timeout;
- командная строка и exit code всех процессов.

Артефакты не являются ожидаемым результатом следующего запуска и не
подменяют native host. Они нужны, чтобы поднять тот же тест на Windows,
повторить один seed и отлаживать алгоритм по фактическому потоку.

## Команда и CI

Тест должен запускаться явно и одинаково локально и в ручном Windows workflow,
например:

```text
go test ./cmd/f4 -run '^TestNativeOpenConsole' -count=1 -v
```

Обычный push не должен случайно скачивать 18 MB и запускать долгий gate. Для CI
добавить отдельный `workflow_dispatch` Windows job с тем же тестом, а для
локальной отладки — тот же `go test` и переменные сохранения артефактов.
Результат считается зелёным только при успешной проверке host, базовых
сценариях и всех 300 seed; skip из-за отсутствия сети, версии или host считается
непройденным gate.

## Граница готовности

Следующим изменением нужно реализовать именно этот нативный test harness и
первый минимальный сценарий. После него расширить сценарии до полного набора,
добавить 300 seed, повтор одного seed и ручной Windows workflow. До фактического
запуска на Windows нельзя заявлять, что ConPTY-алгоритм проверен, а успешная
сборка на Linux или compile-only Windows не является результатом этого gate.
