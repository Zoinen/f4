# Preparation CPU and frame-local vector-gate lookup experiment

Date: 2026-10-21. Branch: `zoin_branch/cached-pixel-grid`.
Goal remains constant 160 Hz without spikes; it is not achieved.

## Accepted CPU and scheduler capture

The deployed retention implementation was captured with the fresh minimal host,
160 Hz, actual DPR 1.75, Downloads, 187 entries, density 152, and rapid wheel input
at 10 ms. Both cold and warm cases completed two ten-second input windows.
Focus, source path, dimensions, input count, and bounded recorder checks passed.
No build, offline analysis, or UI Automation observer ran during input.

The owned kernel session enabled PROC_THREAD, LOADER, PROFILE, CSWITCH, and
DISPATCHER, with CPU stack walking. It reported no lost events/buffers or decode
errors. The trace hashes were verified through compression and offline extraction.
The native sampled-profile prefix decoder was independently compared to xperf:
201/201 cold reference records and 237/237 warm records matched, with zero errors.

The symbol map was generated by relinking the diagnostic without launching the
map binary. Its 41,871,130 bytes of executable code and runtime function table
were byte-identical to those of the captured host. Runtime-function/unwind bounds
and identical-code-folding aliases are retained in the resolver to avoid assigning
unmapped code to an arbitrary neighboring public symbol.

The largest preparation span reproduced in the cold capture:

| Cold block 0 preparation | 6.1646 | 6.1187 | 0.0307 | 0.0152 |

This supports investigation of render-thread preparation work, rather than an
assumption that this tail is primarily waiting to be scheduled. Scheduled time
can include driver work/spinning; it is not proof that all cycles are application
instructions, nor a proof about GPU execution time. The previous untraced 7.873 ms
render-start-to-end frame contained 5.6741 ms preparation and 1.5472 ms submission.
That is a different frame; scheduler attribution must not be transferred to it.

## Frame-local gate lookup prototype: not promoted

`F4VectorGateFrame` performs ancestor walks to classify geometry under vector
gates. The prototype memoizes both positive and negative owner lookups only within
one constructor invocation. It retains no result across frames, reparenting,
node deletion, or gate replacement. The initial implementation uses QHash entries
holding QSharedPointer values. It does not alter admission, priority, readiness,
clipping, renderer dimensions, or the animation clock.

Five native helper tests passed, covering nearest nested owner, nongated branches,
repeated siblings, new-frame reparenting, removal/replacement of a gate, and mixed
paths. Four import-isolation tests and the static Windows DLL audit passed.
These helper tests establish classification consistency, not complete rendered
scene equivalence; the prototype was not considered production-ready from them.

A same-executable runtime switch selects the old traversal or the new cache.
Both accepted arms also use a bounded foreground WinEvent logger without UIA.
The enabled arm ran before control. Both had 4075.142857 cold extent and
3623.142857 warm extent. A prior control attempt lost focus during warm input
and was rejected; its measurements are not substituted for the accepted arm.

| enabled / warm | 0 | 1.0381 / 3.3606 | 1.9105 / 5.3943 / 9.6659 |

Cold performance improved in some metrics, but warm median and tail results were
mixed or worse. The enabled warm maximum reached 9.6659 ms, versus 7.2690 ms
control in block 0. This is not a consistent improvement; **the prototype is not
promoted**. More repetitions could separate run variability, but these results
already reject any claim that this implementation establishes smooth 160 Hz.

A future implementation should avoid simply replacing ancestor walks with a large
per-frame allocated hash of shared owners. Consider raw, constructor-local owner
references or event-invalidated ownership only after confirming their lifetime,
nearest-owner and replacement contracts. Neither alternative is implemented here.
The current prototype remains solely under artifacts; production sources and
Qt dependency policy were not changed in this investigation.

## Presentation timing remains an open measurement question

All observed presents use the composed flip path. PresentMon's version-pinned
[metric definitions](https://github.com/GameTechDev/PresentMon/blob/v2.6.0/README-ConsoleApplication.md)
describe its display intervals and delays; they do not supply a photon capture
of this monitor. The project's older [multi-monitor issue](https://github.com/GameTechDev/PresentMon/issues/108)
documents possible display-timing inaccuracies for some Windows configurations.
That issue does not prove our present capture is inaccurate. The existing motion
gates remain unchanged and failed; no clock change or relaxed threshold follows
from this caveat. Actual presentation/deadline correlation still needs validation.
