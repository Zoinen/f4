# F4: native profile of viewer fly-in / fly-out

Date: 2026-10-07, Europe/Moscow. This is a diagnosis of the currently running
release build, not a before/after benchmark. No application source, binary,
dependency, or runtime rendering backend was changed.

## Result

Two distinct delay paths were captured:

1. **Repeated viewport fitting on the GUI thread.** Every animation step
   changes viewport width and height separately. Both handlers call
   `resizeViewport()` and then `zoomToFit(true)`. In the instrumented callback
   capture these two handlers account for 76.2% of the inclusive QML-animation
   update time during closing and 68.7% during opening. A mid-flight width
   handler takes 35.529 ms wall time, coinciding with a 39.188 ms frame gap.
2. **CPU-side driver allocation / memory reclaim.** Another closing frame
   spends 40.867 ms inside scene-graph rendering, almost entirely scheduled
   on the CPU. Samples in that interval show page allocation/reclaim and
   zswap compression. The GUI thread waits for the render thread for
   26.843 ms. This produces a 43.288 ms frame gap; it is not a long-running
   scaling shader on the GPU.

A separate minimal-event capture, without CPU sampling or the phase/callback
probes, still has a 35.793 ms closing gap and a 60.811 ms start-to-first-frame
delay on one close. Thus the existence of the problem is not solely an
artifact of the heavier capture. Exact timings remain sensitive to paging,
scheduling, instrumentation, and the small sample size.

The first optimization target should be the per-frame viewport-resize/fitting
flow, not another reduction in image quality. Driver resource ownership during
the allocation/reclaim stall remains unresolved and needs a separate targeted
investigation before choosing a cache-lifetime change.

Source:
[GalleryViewerSurface.qml:77](/home/zoin/Documents/Codex/2026-08-31/i-have-f4-project-fork-on/f4/third_party/ZoinGallery/qml/GalleryViewerSurface.qml:77),

```qml
function resizeViewport() {
    // ... previous-size bookkeeping ...
    if (zoomFitView) {
        zoomToFit(true)
    }
    // ... non-fit center preservation ...
}
onWidthChanged: resizeViewport()
onHeightChanged: resizeViewport()
```

The flight interpolates the actual `FlickableZoomable` width and height, not
only a presentation transform. `zoomToFit(true)` stops related animations,
sets scrollbar opacity, calculates a fit, writes zoom and image position,
and writes three animation endpoints. Dependent geometry/property bindings
then execute. This is not merely two cheap arithmetic calculations.

The native callbacks at ELF addresses `0x1302a70` and `0x13022f0` were verified
against the existing generated QML C++ and disassembly: they are the width
and height handlers, using lookup IDs 140 and 141, respectively. The existing
build output exactly matches the running host hash.

During four closes there are 40 width and 40 height handler calls: about two
refits per animation update. During four opens there are 39 of each. Their
ranges do not overlap. The following durations are **inclusive wall time**;
they include nested binding execution, paging, and instrumentation.

The width+height totals occupy 76.2% / 68.7% of their enclosing animation

Final timer updates can include transition completion; the long width
example below is in the middle of the flight, not just cleanup.

At monotonic 264529.253978--264529.289507 the width handler takes 35.529 ms.
Scheduler switches account for 11.600 ms off-CPU, leaving 23.929 ms scheduled
time (still inclusive, not exclusive user CPU). Its QML timer update lasts

the GUI update is unfinished. The frame-end gap is
264529.258911--264529.298099: **39.188 ms**. After the GUI catches up, actual

## Hotspot: driver allocation under memory pressure

At monotonic 264304.244405--264304.285272, `renderSceneGraph()` takes
**40.867 ms** with no recorded render-thread switch-out. During this range,
render-thread IP samples show `__pi_clear_page`, `lzo1x_1_do_compress_safe`,
`find_next_res`, allocator, page-table and reclaim functions. The GUI thread
sleeps waiting for the render thread at 264304.260716--264304.287559:
**26.843 ms**. Frame ends are separated by **43.288 ms**.

The earlier DWARF CPU capture provides the causal kernel chain during
rendering:

```text
ASAHI_VM_BIND -> drm_gem_shmem_get_pages_sgt
 -> drm_gem_get_pages -> shmem_alloc_folio
 -> __alloc_pages_slowpath -> try_to_free_pages
 -> shrink_folio_list -> zswap_store -> zswap_compress
 -> lzo1x_1_do_compress_safe
```

Separate GUI samples also show `do_swap_page -> zswap_load ->
lzo1x_decompress_safe`. These are page-in and reclaim/compression costs,
not FFmpeg decoding or a long GPU scaling pass.

Memory snapshots during this session: system RAM 7.3 GiB, available 1.4 GiB,
swap used 7.2 of 8.0 GiB. An inactive Qt-host snapshot has approximately
34 MiB RSS and 777 MiB `VmSwap`; a later active/paused snapshot has 266 MiB
RSS and 513 MiB `VmSwap`. These are **process/system snapshots**, not QML
GC heap measurements, and do not establish a leak or show that F4 alone
caused system memory pressure. Diagnostic trace buffers and files also use
memory. No other apps were killed and no swap/sysctl configuration was
changed.

The exact Mesa/QSG resource whose allocation triggers the long reclaim is
not identified by these probes. Avoid attributing it to a particular cache,
large texture, Qt bug, or hardware defect without the next allocator-level
trace.

## Recommended next steps, not implemented

1. Separate fly-in/out presentation from the live viewport layout: keep the
   inner viewport's fit stable during the short flight and animate an outer
   presentation transform/clip. A smaller first experiment is to coalesce
   width/height refitting, but avoiding refitting each frame is the stronger
   target. Preserve crop, aspect ratio, interruptions and reversed flights.
2. Trace Mesa buffer allocation/reuse and cache activation/deactivation at
   flight boundaries under the same memory conditions. Identify the resource
   before retaining or preallocating anything; a larger permanent cache could
   worsen the observed paging. Existing RHI texture probes do not establish
   the resource responsible for the VM_BIND reclaim stall.
3. Retain the current hardware-sampling mode only during the flight. Restore
   full-quality resting/playback/pan rendering and complete scene-space pixel
   alignment at both endpoints. Any later layout change needs actual leaf
   geometry/transform checks and rendered-image verification at DPR 1.75.
4. Re-measure paused and playing closes, opens, interrupted/reversed flights,
   first-frame delay, GUI callback cost and idle redraws. Keep minimal-event
   cadence checks separate from detailed attribution traces.

No proposed fix was applied. The canonical app remains running with the clip
paused. Production source changes present before this investigation were
preserved; only diagnostic artifacts/report were created.
